## 안별 설명

### A — 기한순 대조표 (`?variant=a`)

**다건 배열: 평평한 목록 + 한 건의 상세.** 좌측은 문서 기한 오름차순, 동률이면 문서 번호다. 우측은 선택한 문서의 고정된 판정 자료다. 기한 경과를 먼저 보되 재량·법정 판정·입력 대기를 행의 다른 칸에 둔다. 기한을 위험 점수로 바꾸지 않는다.

드러내는 것은 **서로 다른 판단 종류 사이에서도 비교할 수 있는 기한**, 같은 출장의 두 문서, 계산이 결재선에 닿는 과정이다. 초기 선택 P-101 상단에는 조항 원문과 숙박 초과 산식·상향 결과를 붙였다. 계산 전체·원문 블록·두 봉우리 표는 상세를 따라 이어진다.

숨기는 것은 집단별 양의 형태다. 재량이 몰리는지, 특정 증빙 판정이 몰리는지는 B보다 훑기 어렵다. 긴 문서를 읽을 때 세로 이동이 길고 좁은 화면에서는 큐와 상세가 위아래로 바뀐다. 개입은 선택 문서의 책임자 역할에서 승인/동의 또는 질문하고 보류하는 자리다. 값 확정은 별도 입력 대기로 이동해 처리한다.

### B — 판정별 섹션 (`?variant=b`)

**다건 배열: 판정별 섹션 + 롤업.** `증빙 법정 판정 / 정책 대조 / 규칙 대조 완료` 세 열과 `보류 / 승인 카드 도달 전 / 완료·지급` 집계가 있다. 열 안은 기한순이다. 한 문서를 누르면 큐 위에 상세가 열린다.

드러내는 것은 **에이전트가 어디까지 닫았고 어떤 종류의 판단이 남았는가**다. 입력 대기와 완료를 접어도 건수는 남는다. “규칙 대조 완료”는 사람이 승인해야 할 문서이며 자동 승인 묶음이 아니다. 근거를 읽고 판단하는 액션은 A와 동일하다.

숨기는 것은 전역 기한 순서다. 예컨대 S-105의 11/16과 P-101의 11/18을 서로 다른 열에서 읽어야 한다. 판정 불가지만 기록만 하는 S-106과 별도 판단이 필요한 S-107이 같은 열에 있어 표지의 의미를 더 읽어야 한다. 이는 근본적인 분류 비용이다. S-107은 법정 판정 열에 한 번만 놓고 재량 표지를 함께 붙여 문서를 복제하지 않는다.

### C — 한 건 집중 (`?variant=c`)

**다건 배열: 큐 포인터.** 기한순 N/전체 건수, 이전/다음 문서, 접힌 전체 큐와 경과·대기 건수를 보여준다. 상세는 `두 봉우리 / 정책·결재선 / 증빙·출처 / 기한·기록`의 탭으로 나눈다. 상단의 핵심 근거는 탭과 무관하게 유지된다.

드러내는 것은 **현재 판단 대상 하나와 그 판단의 자료**다. 화면이 덜 복잡하고 상세 폭을 확보한다. 숨기는 것은 다른 문서의 구체적인 기한·내용이며, 한 건 안에서도 근거 탭을 이동해야 한다. 다음 건이 더 급한지 보려면 큐 전체를 펼쳐야 한다. 순서대로 누르는 관성을 강화할 수 있으므로 승인 후 자동으로 다음 문서로 넘기지 않는다. 개입은 현재 문서의 액션이며 큐 포인터는 승인이 아니다.

세 안에서 데이터와 현재 선택·문서 상태는 공유한다. B로 바꾸면 상세가 접히지만 상단 상태줄에 선택 문서가 남고 같은 행을 다시 열 수 있다. 역할 변경만 해당 역할의 첫 문서를 선택한다. 전체 역할을 동시에 행사하는 권한 모델을 만들지 않았다.

## 기한 축 분석

### 아무도 안 한 이유부터

**확인한 세 제품에 없다는 것은 시장 전체에 없다는 증명이 아니다.** `docs/research/competitor-screens.md` §0·§4는 공식 캡처 중심이고 국내 제품과 출장관리 제품의 조사가 비어 있음을 명시한다. 왜 없었는지는 조사로 확인된 사실이 아니므로 아래는 설계 가설이다.

1. **기한의 신뢰도가 상태 시각보다 낮을 수 있다.** 출발일·복귀일·자기 차례 도달일·회사 휴일·규정 판이 모두 있어야 계산된다. 한 값이 바뀌면 표시 날짜도 바뀐다. 마지막 갱신 시각보다 계약이 무겁다. 보통 큐처럼 날짜 하나를 입력받으면 근거가 사라진다.
2. **문서 기한과 개인의 처리 기한이 다르다.** 해외 사전승인 완료는 출발 5영업일 전, 각 승인자의 처리는 도달 다음 날부터 3영업일이다. 이를 하나의 숫자로만 보이면 누가 무엇을 놓쳤는지 알 수 없다.
3. **정렬과 에스컬레이션이 쉽게 섞인다.** 빨간 기한을 보면 자동 상향·반려·강제 승인도 있을 것으로 기대한다. 그러나 `PRC-14-3`과 #17이 후속 상태를 열어 두었고 결재선은 기안 시 확정된다. 시각 디자인이 없는 정책을 암묵적으로 약속할 수 있다.
4. **현재 걸린 기한의 집합이 정의되어야 한다.** 이행한 기안 기한을 계속 포함하면 모든 문서가 옛 기한에 고정된다. 반대로 이력을 지우면 늦게 기안했다는 사실을 숨긴다. 현재 적용과 이력 보존은 별개다.

### 그래도 넣는 형태

이 MVP는 기한을 1급 속성으로 이미 선택했으므로 세 안 모두 기한 축을 갖는다. **A의 전역 기한순을 권고한다.** 기한 값과 함께 종류·기준일·방향·영업일 수·조항·판·KST·달력 식별을 보여준다. 현재 적용 기한의 최솟값을 정렬에 쓰고 모든 계산 행을 상세에 남긴다. 동률은 문서 번호로 안정적으로 정한다.

- P-101: 출발 11/25의 5영업일 전 = 11/18. 도달 11/13 다음 날부터 3영업일 = 11/18. 두 의무가 같은 날 18:00에 끝난다.
- S-105: 도달 11/11 다음 날부터 3영업일 = 11/16. 현재 기준 시각에 경과로 표시되지만 재무합의대기를 유지한다.
- E-109: 복귀 11/6 다음 날부터 10영업일 = 11/20. 기안 전이므로 정산 기안 기한이 현재 적용된다.
- S-112: 완료 11/11 다음 날부터 5영업일 = 11/18. 결재 완료 건의 지급 기한으로 표시하며 승인 대기 수에 넣지 않는다.
- 보류는 `PRC-14-1`에서 정한 처리 셋 중 하나이므로 그 처리 기한은 이행으로 남긴다. 답변이 오면 같은 승인자에게 돌아오고 `PRC-14-2`대로 새 도달일부터 계산한다. 보류 중에도 사전승인 완료 의무가 남았다면 그 기한은 남는다.

“임박”은 새로운 정책 문턱을 만들지 않고 **오늘 18:00**이라는 사실로 표시한다. 현재 시각을 18:01로 바꾸면 같은 사례가 경과로 바뀌며 승인 상태는 바뀌지 않는다. 누락된 기준일·달력 범위 밖의 계산은 제품에서 `계산 불가`로 드러내야 하며 임의 날짜로 메우면 안 된다. 이 프로토타입은 필요한 기준일이 있는 2026년 4분기 사례만 실행하고 누락·달력 버전 갱신 UI는 구현하지 않았다.

기한을 넣지 않는 안은 원인의 불신을 숨길 뿐이며 `CONTEXT.md` 승인자 큐 정의·PRD 핵심 기능 1과 맞지 않는다. “기한 계산은 가능하지만 기한에 따른 자동 처리는 미정”이라는 경계를 노출하는 쪽을 택했다.

## 정책 원문을 카드에 싣는 형태

**조항의 이름 → 원문 → 이 건의 숫자 → 결재선의 변화**를 같은 읽기 경로에 놓는다. 원문과 해설을 섞어 인용하지 않는다. 숫자는 원문의 기계 판독 블록에만 있는 경우가 많으므로 산문만 인용해서는 금액의 출처를 보여줄 수 없다.

P-101에서 보이는 연결은 다음과 같다.

1. `여비규정 제6조 제2항 · TRV-6-2 · 판 1`과 문서에서 읽은 축자 본문을 표시한다. 숙박비가 밤별이 아니라 합계 비교라는 조건을 생략하지 않는다.
2. 해당 YAML 원문에 `가` 등급의 직급별 금액과 `compare: 합계`가 보인다. 과장 상한 230,000원 × 4박 = 920,000원과 숙박 청구 2,020,000원을 나란히 놓는다.
3. 초과 1,100,000원 + 다른 여비 3,185,000원에서 한도 적용 금액 4,105,000원, 예상 총액 5,205,000원을 구분한다. “한도 초과”와 “한도 초과 청구”를 섞지 않는다.
4. `TRV-12-1`은 자동 인정할 수 없는 부득이한 사유의 판단이다. 물어볼 사실과 모은 자료를 올라간 결재권자에게 붙인다.
5. `APV-5-2`에서 총액은 본부장, 한도 적용 금액은 팀장. `APV-7-1`로 팀장만 한 단계 올리고 `APV-7-4`로 높은 단계를 선택한다. 두 효과를 더하지 않아 본부장에서 멈춘다.

정산에서는 이 선 위에 **같은 출장의 사전승인 문서 번호·전결권자·인정 범위**를 더한다. S-102의 초과를 다시 상향하지 않는 근거는 `TRV-12-3`이고 본부장 하한은 `APV-7.2-1`이다. S-108은 총액이 같아도 항공 좌석의 차이 행을 강조하고 본인 마일리지 사용 사유와 `TRV-8-2`로 잇는다.

자료 없는 값을 “같음”으로 출력하지 않는 비교 함수를 사용했다. 최소 비교 항목은 총액·네 여비 항목·좌석·숙박 박수·출장 일수·일정·업무일/비업무일·행선지·동행·사적 일정·초과 인정 범위다. 이번 합성 사례는 날짜별 업무 내용과 왕복교통비 안분의 전체 증빙까지 펼치지는 않는다. 그 상세가 필요한 `TRV-13-4` 시나리오는 후속으로 남긴다.

인용 원본 28개 조항은 HTML에 들어 있으므로 파일을 옮겨도 읽힌다. 정책 수정 기능은 없고 원본 파일을 다시 읽지 않는 스냅샷이다. 계산 코드는 화면 실험용으로 그 숫자를 사용하며 제품의 정책 엔진을 대신하지 않는다. 원본·스냅샷의 동기화는 최종 제품에서 다시 구현해야 한다.

## 정책 대조 결과: 주의 신호 vs 별도 구획 — 권고와 근거

**정책 대조는 별도 구획으로 두는 것을 권고한다.** 파이프라인 신호는 법적 하자·판정 불가 두 칸으로 유지한다. 정책의 계산 결과는 읽어야 할 판정 입력이고, 재량·차이의 판단은 이미 결재선에 서 있는 사람의 역할이다. 이를 세 번째 붉은 주의 신호와 별도 확인 버튼으로 복제할 이유가 없다.

이는 **이름만 바꿔 사람의 부담을 숨기자는 제안이 아니다.** `CONTEXT.md`의 주의 신호가 “따로 판단을 요구하는 표시”라는 의미인 만큼 재량도 넓게 읽으면 그 정의에 걸린다. 제품에서 시각적 구획을 분리해도 접촉 비용은 전부 기록해야 한다. 이번 권고는 신호의 분류와 실제 사람 요청을 별개의 집계 축으로 두자는 것이다.

| 대상 | 표시 | 사람 경로 | 집계 |
| --- | --- | --- | --- |
| 한도 안·단독 판독·검산 불가 단독 | 정책 결과 / 검증 수준 | 새 확인 요청 없음. 원래 결재는 남음 | H3~H5 준수. 일반 결재 수는 별도 공개 |
| 새 한도 초과 청구 | 정책 구획에 초과 금액·산식·재량 | 올라간 결재권자의 기존 문서에서 지급 이유 판단 | 정책 판단 문서 수와 실제 추가 요청 수를 기록 |
| 사전 인정 안의 초과 | 인정 금액과 정산 금액 비교 | 재상향·중복 판단 요청 없음 | 재량 요청을 하나 더 만들지 않음 |
| 계획과 다른 좌석 등 | 차이 행·사유·조항 | 기존 결재권자의 업무상 필요 판단에 포함 | 차이 건수와 그로 인한 추가 질문을 분리 |
| 법적 하자 | 파이프라인의 법적 하자 칸 | 치유·근거 확인이 필요한 승인자 | 기존 R2의 추가 판단 고유 지출에 포함 |
| 판정 불가 + 대사 완료 | 판정 불가 1건, 기록만 / 추가 판단 0건 | `PRC-13-1`~`PRC-13-3` 기록 경로 | 표시된 것만으로 R2에 넣지 않음 |
| 판정 불가 + 대사 완료 아님 | 판정 불가 칸과 정책 구획의 같은 판단 연결 | `PRC-13-4` 보류 질문, 답변 뒤 `PRC-13-5` | 고유 지출은 R2 합집합에서 한 번. 실제 재요청은 R3에서 각각 |
| 수기 확정 / 짝 보류 | 승인 카드 도달 전 대기 | 기안자 또는 막힌 이유에 따른 재무합의자 | R1·R2 분자, 단계별 실제 요청 R3, 배정 R4. 대기도 분모에 남음 |

**R2는 현 정의를 유지한다.** 분모는 접수된 고유 지출, 분자는 수기 확정·짝 확인·H11 두 종류로 별도 판단을 요구한 지출의 합집합이다(`docs/design/receipt-pipeline.md:2512-2521`). 정책 대조 전체를 여기에 넣지 않는다. 사전승인은 아직 실제 지출이 없고 재량 한 건이 여러 지출을 포괄할 수 있어, 무리하게 섞으면 단위부터 깨진다. ≤15%는 초기 검증 가정이며 신호 표시율이 아니다.

**ADR-0010을 충족하려면 R2만 보여줘서는 안 된다.** #11에 다음을 함께 넘긴다. 기존 R1~R4의 정의·분모를 유지하면서, (a) 일반 승인/동의 문서 수, (b) 정책 때문에 추가 판단이 필요한 고유 문서 수, (c) 정책에서 발생한 실제 추가 질문·확인·재요청 횟수, (d) 책임자별 배정량을 별도 공개한다. 정책으로 실제 발생한 추가 확인은 R3·R4의 추가 작업에서 숨기지 않고 원인 태그로 나눈다. 기존 결재 한 번에 포함된 판단과 추가 접촉 한 번을 같은 수치로 세지 않는다. 새 문서 단위 비율의 모집단·상한은 #11이 정하며 여기서 15%를 복사하지 않는다.

재량 조항 넷의 경로는 그대로 따른다. 새 “정책 담당자”나 별도 승인 큐를 만들지 않는다.

| 조항 | 사람에게 모을 것 | 판단 책임자 | 자동 확정하면 안 되는 것 |
| --- | --- | --- | --- |
| `TRV-7-1` | 동행·동일 숙소·직급 상한 차이, 함께 수행한 업무와 대체 숙소를 쓰지 않은 이유 | 결재권자 | 같은 숙소의 업무상 필요, 상위 직급 상한 적용 |
| `TRV-12-1` | 초과 금액·사유·대체안 견적·동행자 요금 | 올라간 결재권자 | 부득이한 사유 인정, 초과분 지급 |
| `TRV-13-4` | 업무일/비업무일·날짜별 업무·목적, 업무/사적 일정의 선후 | 결재권자 | 직접 동기 판단, 왕복교통비 안분 |
| `PRC-13-5` | 보류 질문 뒤에도 남은 쟁점, 실제 지출·업무 관련성을 뒷받침하는 자료 | 재무합의자 | 사내 지급 동의, 법정 값 변경, 결재권자의 업무상 필요 판단 대체 |

예산을 넘으면 필요한 확정을 버리거나 승인 카드로 밀어 넣지 않는다. 실제 송부·대기·미완료·자동 진행 가능 수를 공개하고 해당 접수 확대·배치를 멈춰야 한다(ADR-0010). 이 화면의 편향된 12사례로 상한 통과를 주장하지 않으며, 대기 2건을 정상 문서로 올리지 않는다. 상한을 감시·차단하는 운영 엔진은 이 UI 시연에 없다.

반대로 정책도 주의 신호로 부르기로 사람이 선택한다면, H11의 범위를 파이프라인으로 유지하면서 신호 원인을 구분해야 한다. R2에 그대로 합산할지부터 문서/지출 단위 문제를 해결하고 ADR-0010·#11의 정의를 함께 갱신해야 한다. 색 하나 추가하는 변경으로 끝나지 않는다.

| 평가 축 | A 기한순 대조표 | B 판정별 섹션 | C 큐 포인터 |
| --- | --- | --- | --- |

## 권고안 1개와 이유

**A — 기한순 대조표를 권고한다. 최종 선택은 사람이 한다.** #8은 HITL 티켓이며 이 문서는 선택을 확정하지 않는다.

이유는 PRD의 문제 문장에 가장 직접 닿기 때문이다. 한 건이 어느 조항·사전승인 항목과 어긋났는지를 보면서도, 옆의 다른 건이 어떤 기한과 상태에 있는지 놓치지 않는다. 기한이 왜 그 값인지 설명하는 자리를 유지하고, 재량·대사 대기·법정 하자를 같은 경고로 접지 않는다. B의 장점인 대기·완료 수의 집계는 A 상단에도 있지만 주 배열은 기한순으로 일관된다.

다만 A에서 가장 먼저 검증할 반증은 **상세의 길이 때문에 조항이나 근거를 읽지 않고 액션으로 내려가는가**다. C처럼 좁은 집중 화면이 더 낫다는 관찰이 나오면 권고가 바뀔 수 있다. 재량 판단 누락·두 봉우리 차이 발견·대기 발견·책임자 식별로 비교해야 하며 시간 절감은 선택 근거로 쓰지 않는다.

## “채팅창 하나”를 왜 기각하는가

사람이 질문하는 문장에는 채팅이 맞을 수 있다. 그래서 보류에는 자유로운 질문을 남겼다. 그러나 전체 척추를 채팅 기록으로 두면 다음 네 가지가 계속 사라진다.

- **동시 진행의 현재 상태:** 세 문서에 번갈아 답변이 오면 발화 순서와 기한 순서가 다르다. A는 갱신 시각이 아닌 현재 의무의 기한으로 문서를 다시 계산한다.
- **두 문서의 대조 단위:** S-108은 총액이 같아도 좌석이 다르다. 대화 요약은 “총액 동일”로 축약할 수 있지만 비교표는 좌석 행을 남긴다.
- **인용의 범위:** “한도 초과입니다”라는 답변만으로는 과장·가 등급·4박·합계 비교·상향 사유가 연결되지 않는다. 원문 옆의 입력과 산식이 그 연결을 고정한다.
- **누가 어떤 권한으로 행동하는가:** “진행해” 한마디로 수기 확정·동의·승인을 구별할 수 없다. 입력 대기는 값을 닫고, 재무합의는 근거를, 결재권자는 업무상 필요를 본다.

`docs/research/competitor-screens.md`와 캡처 9장을 직접 열어 확인했다. Agent Inbox의 목록은 실행 상태 중심이고, Ramp는 정책 근거가 들어 있는 구조화 카드·대량 집계를, Moveworks는 구조화 카드와 큐 포인터를 보여준다. 채팅이 아닌 것 자체는 차별점이 아니다. 채팅 안에도 구조화 카드를 넣을 수 있으나, 그 카드가 위 네 가지를 유지하면 이미 “채팅창 하나”라는 대안보다 도메인 표면에 가까워진다.

## ADR·PRD·CONTEXT.md와 충돌하거나 긴장하는 지점

1. **“걸린 기한”의 적용 범위가 원문에 없다.** `PRC-3-5`는 이행한 기한을 빼는지 명시하지 않는다. 코디네이터 확인을 받아 현재 의무만 정렬에 넣고 이행한 기한은 이력으로 보존했다. 이것은 규정이 이미 명료하다는 주장이 아니다. 또한 `PRC-6-2`는 늦게 기안한 문서의 기한을 출발일로 쓰지만 출발일 자체가 `kind: deadline` 블록으로 정의되지 않았다. 이 예외는 이번 실행 사례에 넣지 않았고 임의로 여섯 번째 사내 기한을 만들지 않았다. 규정 보완은 사람의 결정 이후다.
2. **승인자 큐에 승인 전 대기를 얼마나 보일 것인가.** `CONTEXT.md`의 큐는 승인 카드 목록이지만 ADR-0010은 미완료·대기를 공개하라고 한다. 이 시연은 같은 표면 안의 별도 구획·표식으로 보여주되 승인 카드로 부르지 않는다. 기안자 역할에서는 승인자 큐가 아닌 “승인 전 입력”의 영역으로 읽어야 한다. 본제품의 접근권한·이동 위치는 #10이 정해야 한다.
3. **주의 신호의 넓은 정의와 정책 구획의 실질적인 판단 요구.** 별도 구획으로 분류해도 재량은 사람이 판단한다. H11/R2에서 빼었다고 사람이 덜 일하는 것은 아니다. 일반 결재·정책 판단 문서·실제 추가 접촉을 함께 공개하고 #11에서 측정 단위를 확정해야 한다.
4. **가장 이른 기한과 보류의 긴장.** 보류는 결재 처리를 한 것이지만 출장 전체의 완료 의무는 여전히 걸릴 수 있다. 보류 답변이 오지 않는 경우의 에스컬레이션·상태 이름은 #17 미결이다. 이 화면은 질문 대기를 유지하고 자동 전환하지 않는다.
5. **재량이 금액·결재선 입력을 바꿀 수 있다.** `TRV-7-1`의 상위 상한 적용이나 `TRV-13-4`의 안분 판단은 금액에 닿는다. `APV-11`은 결재선을 바꾸는 수정을 재기안으로만 허용한다. 이번 작동 경로는 기안 금액을 바꾸지 않는 P-101의 초과 인정과 S-107의 근거 판단으로 제한했다. 액션에서 금액을 즉석 수정하거나 결재선을 다시 쓰는 기능을 만들지 않았다.
6. **정책 원본과 자기완결 파일.** ADR-0005는 정책의 두 벌을 막는다. HTML은 원본을 대체하는 데이터 파일이 아니라 오프라인 화면 실험용 읽기 전용 복제다. 이를 제품 코드로 승격하면 충돌한다. 사람 선택 후 원본에서 파생·인용하는 제품 구현을 새로 해야 한다.
7. **실제 증빙 추출 기능과 UI 도식.** ADR-0009의 크롭/원본 상호작용을 도식으로 시연했으며 실제 OCR·좌표 품질·PDF 래스터화·환율 정확도를 검증하지 않았다. 공급 장소·검증 수준·법정 판정은 합성 upstream 결과다. S4의 원문 문자열 검증과 S9의 추출 품질 검증은 다른 것이다.
8. **반려 권한과 비활성 자리.** `APV-9-3`의 항상 반려 허용을 부정하는 설정이 아니다. #17 후속 상태가 미정이라 이 프로토타입에서만 액션을 제공하지 않는다. 원문에 반려 문장이 있는 것은 그대로 인용하지만 반려 흐름은 설계하지 않았다.
9. **프로토타입 스킬의 기본 보존 방식과 이번 소유권.** 스킬의 브랜치 커밋·이슈 기록 대신 사용자 지시대로 지정 폴더의 작업 트리에만 남긴다. 규정·용어집·ADR·PRD를 고치거나 GitHub에 쓰지 않는다. `graft map`·`graft ask --source`는 인덱스가 0건이라 지정 문서를 직접 읽었다. 소유권 밖의 그래프 파일은 만들지 않았다.

## 열린 질문 / 다른 티켓으로 넘길 것

- **#8 / 사람 선택:** A 권고를 받아들일지, B의 종류별 시야나 C의 집중 형태가 필요한지. 정책 구획 권고와 “주의 신호”의 의미 경계를 함께 선택한다.
- **#17:** 반려 후 상태, 답변 없는 보류, 기한 경과 뒤 처리, 재량 결과가 재기안을 요구하는 경로, 부분 승인·반환 방법. 이번 시연에서 빈 부분을 성공 상태로 채우지 않았다.
- **#10:** 개인 큐와 기안자 수기 확정 화면의 접근권한, 기한 기준일·달력의 출처/버전, 실제 모의 커넥터 계약, 감사 기록 필드, 증빙 크롭의 실제 데이터 연결. 큐에서 상한 초과 중단·접수 확대 제한이 어떻게 이어지는지도 필요하다.
- **#11:** 지출 단위 R1~R4와 문서 단위 정책 판단을 함께 설명하는 모집단·중복 제거·상한. 편향된 사례 12건을 성능 표본으로 쓰지 않는다. 정상 비율이 낮다고 필요한 판단을 줄이는 경로를 허용하지 않는다.
- **#12:** 긴 원문·여러 기한·필드 표가 겹칠 때의 정보 밀도, 작은 화면의 우선순위, 키보드·보조기기 접근성. 색만으로 구별하지 않는 원칙은 유지한다.
- **용어집 후속:** `현재 걸린 기한`, `승인 카드 도달 전`은 이번 UI의 설명 문구이며 새 도메인 상태로 확정한 이름이 아니다. `재검산·대사 대기`도 실제 상태 기계의 새 enum이 아닌 실행하지 않은 다음 과정의 표시다. 문서/지출/접촉 건수의 이름도 #11과 함께 고정해야 한다.
- **추가 시나리오:** 동행 상한 재량 `TRV-7-1`, 사적 일정과 왕복교통비 재량 `TRV-13-4`, 늦은 사전승인 `PRC-6-2`, 자료 누락·달력 갱신·상한 초과의 동작 실험. 이번 산출물의 작동 사례인 척하지 않는다.

## 검증

- **필수 수용 검사:** 저장소 루트에서 지시된 파일 존재, 외부 리소스 없음, 금지 CSS/문구 없음, `variant` 전환, 인용 식별자 존재, 소유권 밖 변경 없음 검사를 모두 통과했다. 산출물은 `index.html`과 이 문서뿐이다. 커밋·GitHub 쓰기는 하지 않았다.
- **원문 대조:** HTML에 실은 조항 28개의 원문과 기계 판독 블록이 `docs/company/*.md`의 실제 문자열과 일치함을 확인했다. 합성 사례와 환율·증빙 도식은 규정 원문과 구분해 표시한다.
- **브라우저:** 설치된 Google Chrome 153.0.8010.50을 헤드리스로 실행하고 DevTools Protocol로 `file://`의 `?variant=a`, `?variant=b`, `?variant=c`를 각각 열었다. 세 안에서 동일 사례 12건과 상세의 모든 탭을 열었으며 페이지 예외 0건, 콘솔 오류 0건, 외부 HTTP 요청 0건이었다. 인라인 JavaScript 구문 검사도 통과했다.
- **화면 확인:** 1512×1000에서 세 안의 스크린샷을 직접 확인했다. 390×844에서도 각 안의 문서 너비가 화면 너비 390px와 같아 가로 넘침이 없었다. 이는 접근성·실사용 검수 완료를 뜻하지 않는다.
- **상호작용 확인:** 안 전환 후 선택·메모리 상태·URL 유지, 역할별 액션 제한, 보류 후 같은 큐 유지, 답변 도착 후 처리 기한 재계산, 다음 결재권자로 이동, 마지막 승인 완료를 확인했다. 재무합의에서 끝낸 재량 판단이 다음 결재권자에게 중복 요구되지 않으며 `판정 불가` 기록은 그대로 남는다.
- **승인 전 입력과 제약:** 추출 불확실 날짜의 수기 확정·원본 열람 기록, 짝 보류의 서로 다른 통화 유지와 재대사 대기, 18:01 시각에서 기한 경과 표기, 모든 반려 버튼의 비활성·`#17 대기`를 확인했다. 수기 확정이나 짝 확인이 승인 완료로 넘어가지 않는다.
