# ADR-0021 — 모의 커넥터는 셋이고 모두 읽기 전용이며, ERP는 흉내 내지 않는다

- **상태**: Accepted
- **날짜**: 2026-09-22
- **맥락 티켓**: #10 (결정), #1 (실연동 제외), #18 (카드 명세의 요구 칸), #16 (계정 분류의 경계), #11 (실패 주입)

## 맥락

이 MVP는 실 시스템 대신 모의 커넥터를 부른다. 흉내 낼 후보는 as-is 4계통이다 — 한성워크(결재·근태), ERP·회계(전표·지급), 여행사 예약 대행(이메일), 법인카드사 웹(월 단위 수동 다운로드)
(`docs/company/tools.md:11-16`, `CONTEXT.md:343`). 목록과 충실도는 #10에 넘어왔다(`docs/PRD.md:87`, `:174`).
같은 표가 회계 장부의 계정 분류도 #10에 넘겼다(`docs/PRD.md:174`). 증빙 파이프라인은 카드 명세가 가져야 할 칸을 #10에 요구했다(`docs/design/receipt-pipeline.md` §7.5).
[ADR-0011](0011-messages-api-direct-waits-are-document-state.md) 반증 3은 "커밋 전 부작용의 재시도를 멱등 key로 막을 수 없다"다(`docs/adr/0011-messages-api-direct-waits-are-document-state.md:93`).

세 레인은 두 가지에 합의했다. 커넥터는 as-is 형태(비구조 메일, 카드 파일)를 흉내 내고 실 API·발권·송금이 없다.
한성워크 모의에 두 번째 결재 상태를 두지 않고, 앱 DB가 결재의 유일한 원장이다(A8).

갈린 것은 둘이다(비교 문서 D5·D6).

- 목록: codex와 grok은 4계통을 다 두었다. codex는 ERP의 전표·지급 기록과 환율표, 한성워크의 조직·일정·결재 결과 투영·회사 달력을 준다(codex §4.1).
  grok은 지급 처리 커밋 뒤 outbox가 모의 전표 한 장을 쓰고, 한성워크에 근태 행을 쓴다(grok §5.3). claude는 ERP를 만들지 않고 셋 다 들어오기만 한다(claude §4.4).
- 카드 내역: codex와 grok은 as-is 그대로 월 단위 파일을 사람이 반입한다. claude는 이용 내역을 매일 자동으로, 청구 명세를 월 1회 사람이 가져온다(claude §4.4.1).

사용자가 U3(3개·읽기 전용·ERP 없음·계정 분류 안 함)과 U4(이용 내역 매일 + 청구 명세 월 1회)를 골랐다. 둘 다 코디네이터 추천과 같다(비교 문서 `:177-178`).

이 ADR에서 **비교 문서**는 `docs/research/agent-architecture-comparison.md`다. A1–A15는 그 문서 `:48-62`, U1–U6은 `:175-180`, C1–C9는 `:191-199`, D1–D9는 `:75-147`에 있다.
레인 인용(codex·grok·claude §N)은 비교 문서 §0(`:11-19`)이 가리키는 #10 제안서의 절이다.

## 결정

1. **모의 커넥터는 셋이다. ERP·회계는 흉내 내지 않는다**(U3).

   | 커넥터 | 주는 것 | 들어오는 방식 | 값의 출처 |
   | --- | --- | --- | --- |
   | 법인카드사 웹 | 이용 내역 파일, 청구 명세 파일 | 이용 내역은 매일 자동(시스템 작업). 청구 명세는 월 1회 재무가 사람의 명령으로 가져온다 | `시스템 연동` |
   | 여행사 메일함 | 견적서·확정서·변경 통보 메일의 원문과 첨부 | 수신해 원문을 보존한다. 판독은 판독기가 한다([ADR-0018](0018-two-model-contracts-no-side-effect-tools.md)) | 판독한 값은 `에이전트 추출` |
   | 한성워크 | 조직 정보 스냅샷 | 스냅샷 동기화 | `시스템 연동` |

2. **셋 다 들어오기만 한다.** 우리 쪽에서 모의 시스템으로 쓰는 커넥터가 없다. 예약 요청 메일 발신, ERP 전표 생성, 근태 기록 쓰기가 모두 없다(U3, claude §4.4 원칙 1).
   그래서 ADR-0011 반증 3이 생길 자리가 없다.
3. **as-is의 형태를 흉내 낸다**(A8). 메일은 비구조로(`docs/company/tools.md:15`, `:52-53`), 카드는 파일로(`:16`) 둔다. 실 API·발권·송금은 없다(`docs/PRD.md:132-133`).
4. **한성워크 모의에 두 번째 결재 상태 기계를 두지 않는다. 앱 DB가 결재의 유일한 원장이다**(A8).
   결재권자는 한성워크 대신 승인자 큐에서 결재하고(`docs/PRD.md:24`), 근태 반영은 이 제품의 상태 전이다(`docs/PRD.md:27`). 그래서 한성워크에서 가져올 것은 조직 정보뿐이다(claude §4.4.3).
5. **카드 이용 내역은 매일 자동으로 가져오고, 청구 명세는 월 1회 재무가 가져온다**(U4).
   매일 가져오기는 시스템 작업이고, 책임자는 배정된 카드 수집 담당이다(비교 문서 `:185`, [ADR-0019](0019-non-approval-owner-is-assigned-operations-person.md)).
   as-is 문서의 "월 단위 **수동 다운로드**"(`docs/company/tools.md:16`)는 고치지 않는다. 매일 가져오기는 to-be 개선이다(비교 문서 `:178`).
6. **카드 파일의 깨진 줄은 그 줄만 격리한다. 파일 전체를 거부하지 않는다**(C6).
7. **값의 출처에 칸을 더하지 않는다.** 모의 커넥터가 넘긴 구조화 값은 `시스템 연동`이고, 모의 커넥터가 넘긴 문서(여행사 메일)에서 읽은 값은 `에이전트 추출`이다(`CONTEXT.md:345`).
8. **카드 명세는 §7.5의 여섯 칸에 더해 `CardLine`이 요구하는 카드 끝 4자리·청구 원화·가맹점명을 준다**(`82f02d8`의 `docs/design/receipt-pipeline.md:1798-1810`).
   §7.5가 이 셋을 빠뜨린 것은 세 레인이 같이 찾았다(비교 문서 `:67`). 가맹점 업종은 `CardLine`에도 칸이 없어 #18 후속으로 넘긴다(비교 문서 `:214`). **보완(#26, 2026-09-23)**: 칸을 두지 않는다. `CardLine`은 이용 내역의 칸만 갖는 대사 입력이 되었고 청구 원화는 `CardBilling`으로 갔다. 카드 사용자와 수집 기준일을 요구 칸에 더했다([ADR-0031](0031-reconciliation-pending-states-and-input-driven-rerun.md) 결정 4·6).
9. **이 MVP는 회계 장부의 계정 분류를 하지 않는다**(U3). 에이전트의 몫도, 코드의 몫도 아니다(claude §7.3).

## 근거

**왜 ERP가 없는가.** 판정이 읽는 ERP 값이 없다. 지급 처리는 재무팀의 상태 전이이고(`docs/PRD.md:25`, `:86`), 회계 장부의 원화 금액은 확정하지 않는다(`docs/PRD.md:136`).
규정도 "회계 장부에 적을 원화 금액은 이 규정이 정하지 않는다"고 적는다(`TRV-14-3`, `docs/company/travel-policy.md:326`). 이 논거는 claude §4.4.4다.
쓰는 커넥터를 두지 않으면 ADR-0011 반증 3도 닫힌다(비교 문서 `:116`).

**잃는 것.** 무대 4계통 중 ERP가 화면에 한 번도 나오지 않는다. 틈 ③(`docs/company/tools.md:40-44`)은 증빙 파이프라인·대사와 재무팀의 지급 처리 상태 전이로 끝난다(claude §4.4.4).
`docs/company/tools.md:50`의 "넷은 인사·총무·재무 세 경계를 전부 만들어 내는 최소 개수다"는 as-is 무대의 문장이고 커넥터 수의 문장이 아니다(claude §4.4.4, 비교 문서 `:116`).

**왜 이용 내역을 매일 받는가.** 정산 기안 기한은 복귀일부터 10영업일이다(`PRC-10-1`, `docs/company/travel-procedure.md:166-175`).
월 명세만 받으면 그 기한 안에 명세가 오지 않는 출장이 흔하다. 그러면 교차 확인(H3)이 사라지고 대사가 상신 뒤로 밀린다(비교 문서 `:124`, claude §4.4.1).
대사의 비교축은 청구액이 아니라 이용금액(원거래 통화)이고(`CONTEXT.md:309`), 이용금액은 승인 시점에 이미 있다(claude §4.4.1).
카드사 기업 웹은 기간을 지정한 승인·이용 내역 조회와 엑셀 다운로드를 제공한다(비교 문서 `:125`, 출처 `:218-222`). 매일 가져오기는 기술 가능성의 주장이 아니라 **가상 회사 운영의 선택**이다(비교 문서 `:125`).

**왜 두 번째 결재 상태를 두지 않는가.** 앱 DB가 결재의 유일한 원장이다(A8). 한성워크에서 하던 결재는 승인자 큐로 옮긴다(`docs/PRD.md:24`). 결재 상태가 둘이면 큐와 감사가 어긋난다. 내구 실행 계층을 두지 않은 이유(`docs/adr/0011-messages-api-direct-waits-are-document-state.md:74-75`, grok §3.3)에서 끌어온 유추다.

**왜 계정 분류를 하지 않는가.** 계정 분류는 회계 장부의 일이다. 이 MVP는 장부 원화를 확정하지 않고, ERP 커넥터도 없다(claude §7.3).
여비가 아닌 지출은 분리까지만 한다(`docs/PRD.md:137`, `TRV-10-1` `docs/company/travel-policy.md:218`). 분류 규칙을 두려면 규정 원본에 조항이 먼저 있어야 한다(`docs/adr/0005-policy-source-of-truth.md:30-32`, `docs/PRD.md:138`).

**왜 깨진 줄만 격리하는가.** 파일 전체를 거부하면 한 줄의 결손이 같은 파일의 다른 줄의 대사까지 멈춘다 `[유도]`. 격리한 줄은 0건으로 치지 않고 드러낸다(codex §4.1, claude §4.4.1).

| 기각한 대안 | 기각 이유 |
| --- | --- |
| 4계통 — ERP(전표·지급 기록, 합성 환율표), 한성워크(조직·일정·결재 결과 투영·근태, 회사 달력)(codex §4.1) | 판정이 읽는 ERP 값이 없다(claude §4.4.4). 사용자가 U3을 골랐다 |
| 4계통 — ERP는 지급 처리 뒤 outbox가 모의 전표 한 장, 한성워크는 근태 행 쓰기(grok §5.3) | 판정이 읽지 않는 행을 만든다(claude §8 ADR-0021 후보의 "ERP 출력 전용 sink"). grok은 커밋 뒤 outbox라 반증 3이 열리지 않는다고 적었다(grok §5.1). 이 ADR은 쓰는 커넥터를 두지 않아 그 자리를 없앤다 |
| 카드 명세를 as-is 그대로 월 1회 사람이 반입(codex §4.1, grok §5.3) | 정산 기안 기한 안에 대사가 돌지 않는다(비교 문서 `:124`) |
| 거래 단위 실시간 피드·카드 웹훅(claude §9 Q3 c, grok §9 ADR-0020 후보 기각 열) | as-is의 틈이 무대에서 사라진다(claude §9 Q3) |
| 필수 헤더가 빠지면 파일 전체 거부(grok §5.3) | C6 — 깨진 줄만 격리한다 |
| 결손 행이 있는 batch를 통째로 staging에 남김(codex §4.1) | C6 — 깨진 줄만 격리하고 나머지 줄은 들어온다 |
| 그룹웨어 결재 엔진을 따로 둠(grok §9 ADR-0020 후보, codex §8 0020) | A8 — 앱 DB가 결재의 유일한 원장이다 |
| 모의 계정 8구획(codex §7.2), 계정 7종(grok §8.3) | U3 — 이 MVP는 계정 분류를 하지 않는다 |

## 결과

- **반증 조건.** 아래 중 하나가 관측되면 이 결정은 틀렸다.
  1. #11의 시나리오가 ERP에만 있는 사실을 판정 입력으로 요구한다(예: 가지급금 잔액). 그러면 ERP 읽기 커넥터가 필요하다(claude §4.7-1).
  2. 실제 법인카드 웹이 이용 내역을 수시로 주지 않는다는 것이 확인되고, 사용자가 as-is 충실도를 우선한다(claude §4.7-2).
  3. 카드 정상 픽스처에서도 요구 칸이 없거나, 이메일 대신 숨은 구조화 정답을 읽어야 S1·S12가 성립한다(codex §4.3 "추천이 틀리는 조건").
  4. 앱과 모의 시스템 사이의 상태 충돌이 반복된다(codex §8 0020).
  5. 시드만으로 틈 ①·②·③(`docs/company/tools.md:25-44`)이 재현되지 않는다(grok §9 ADR-0020 후보).
  6. 메일 판독값의 총무 백지 입력이 사람 호출을 늘려 R3·R4를 넘긴다(claude §4.7-3).
- ADR-0011 반증 3은 이 결정으로 생길 자리가 없다. 남는 외부 호출은 Anthropic API뿐이고, 업무 부작용이 아니라 비용 부작용이다(claude §4.1).
- 무대 문서의 #10 포인터(`docs/company/tools.md:7`, `docs/company.md:97`)는 이 ADR이 답한다. 두 줄에는 이 ADR을 가리키는 완료 포인터만 붙였다. as-is 기록인 카드 명세의 월 단위 수동 다운로드(`docs/company/tools.md:16`)는 고치지 않았다(U4).
- 여행사 예약의 결제가 누구의 법인카드에 걸리는지는 문서에 없다 — `docs/company/tools.md:36-37`은 예약 확정과 카드 결제가 따로 일어난다고만 적는다(claude §4.4.2). 그 카드 줄의 짝 확인 담당은 #18 후속으로 넘긴다(비교 문서 `:164`, `:214`). **보완(#26, 2026-09-23)**: 총무팀이 관리하는 카드에 걸린다고 두고 `[설계 가정]`, 그 줄의 짝 확인(경쟁·대조 불가·후보 복수·고른 줄을 잃음)은 배정된 총무 예약 담당이다([ADR-0031](0031-reconciliation-pending-states-and-input-driven-rerun.md) 결정 7).
- 칸·주기·실패 주입의 표는 `docs/ARCHITECTURE.md` §9다.
- 기존 결정과의 관계.
  - [ADR-0011](0011-messages-api-direct-waits-are-document-state.md): 반증 3(`docs/adr/0011-messages-api-direct-waits-are-document-state.md:93`)이 생길 쓰기 커넥터가 없다.
  - [ADR-0012](0012-transition-audit-provenance-in-one-transaction.md): 커넥터 출력은 시스템 명령으로만 들어오고, 필드 출처는 3값을 유지한다(`docs/adr/0012-transition-audit-provenance-in-one-transaction.md:41`).
  - [ADR-0013](0013-postgres-object-storage-isolated-by-world-id.md): 커넥터가 가져온 행과 원문은 세계(`world_id`)에 묶인다.
