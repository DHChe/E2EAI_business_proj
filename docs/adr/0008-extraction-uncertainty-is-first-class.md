# ADR-0008 — 추출의 불확실성을 1급으로 되돌린다

- **상태**: Accepted
- **날짜**: 2026-09-21
- **맥락 티켓**: #18 (결정), #19 (근거), #15 (판정 3분할), #11 (지표)

## 맥락

이식 원본인 `slipscan` 저장소는 **판독 신뢰도 표시를 명시적으로 제외했다.**

> `slipscan:phases/1-documents/step2.md:129` — "추출 필드를 늘리지 마라(사업자등록번호·공급가액·부가세·승인번호·메모, 품목, **신뢰도 점수**). 이유: PRD 10.1에서 제외했다."
> `slipscan:docs/PRD.md:257` — "판독 신뢰도 점수와 \"확인 필요\" 배지 | 대신 항목별 \"금액 미인식\"·\"날짜 추정\"·\"중복\" 표시로 대체"

**그 결정은 그 제품에서 옳았다.** 판단 기준이 `slipscan:docs/PRD.md:25`에 적혀 있다 —
"이 다섯 단계(J1)에 쓰이지 않는 기능은 10.1로 보낸다". 시연 5분 여정에서 불확실성을 **소비하는 곳이 없었다.**
통계·보고서·중복 감지 어디도 그 값을 읽지 않았고(`slipscan:docs/PRD.md:246`의 같은 논리),
남은 표시는 통계에서 제외한다는 뜻의 배지 두 개뿐이었다(`slipscan:docs/PRD.md:69, 71`).
잘라낸 근거가 "필드가 판정에 쓰이는가"였다는 점이 중요하다 — **이 MVP에서는 같은 기준이 반대 답을 낸다.**

이 MVP가 보장하기로 한 것은 세 실패 중 **C — "틀렸다는 걸 아는 것"**이고(#18 본문),
척추는 승인자 큐다(#5 결정 9). 승인자가 30건을 훑을 때 불확실한 3건이 표시되지 않으면 그냥 승인한다.

## 결정

**추출의 불확실성을 1급 출력으로 만든다. 단, 그 형태는 신뢰도 점수가 아니다.**

1. 값 하나를 세 칸으로 쓴다 — `raw`(지면 문자열) · 값 · `_status`(`read`/`ambiguous_separator`/`ambiguous_date_locale`/`unreadable`/`absent`).
   모든 칸은 required이고, 모름은 침묵이 아니라 **발화**로 표현된다.
2. 불확실성의 판정은 모델의 자기보고가 아니라 **코드의 규칙**이 한다 —
   지면 문자열 재파싱, 통화 최소단위, 구조적 검산, 단계 간 대조, 법인카드 명세와의 대사.
3. **(i) 추출 불확실**과 **(ii) 법적 하자**를 다른 타입으로 둔다. (i)은 정책 대조 이전에 닫히고, (ii)는 판정 결과로 남는다.
4. 정책 대조·법정 판정은 `_status`가 없는 타입(`Confirmed<T>` · `PolicyFacts`)만 받는다. 경계를 문서 약속이 아니라 **타입**으로 만든다.
5. 사람에게 보내는 건 **판정 입력 필드**로 한정하고, 화면에 에이전트의 값을 미리 채우지 않는다.

설계 본문은 [`docs/design/receipt-pipeline.md`](../design/receipt-pipeline.md).

## 근거

**신뢰도 점수를 되살리지 않는 이유.** #19가 1차 자료로 두 경로를 닫았다 —
Claude Messages API에는 `logprobs`에 해당하는 파라미터도 응답 필드도 **없고**,
자기보고 신뢰도는 과신이 회로 수준에서 관찰되고 RLHF가 유발하며 VLM 문서추출 벤치마크에서 모델별 편차가 극단적이라
**단독 게이트로 쓸 수 없다**. 남는 것은 구조적 검산이다. 즉 SlipScan이 뺀 `신뢰도 점수`라는 물건 자체는
이 MVP에서도 채택하지 않는다 — 뒤집는 것은 **"불확실성을 출력하지 않는다"는 결정**이지 점수의 형태가 아니다.

**왜 `null`로는 안 되는가.** `null` 하나에 "못 읽었다 · 규칙상 판별 불가 · 지면에 없다"가 뭉개진다.
셋은 후속 처리가 전부 다르다 — 재촬영 / 사람 확정 / 정상. 특히 마지막이 중요하다:
계산서에 세액란이 **없는 것은 정상**이고(소득세법 시행령 §211①), 그것을 결손으로 읽으면 정상 문서가 하자로 찍힌다.

**왜 required + 명시적 sentinel인가.** 구조화 출력에는 요청당 optional 24개·union 16개 상한이 있고,
초과하면 `400 Schema is too complex for compilation`이다. 공식 권고가
"필드를 required로 만들고 모델이 명시적으로 `null`/`unknown`을 쓰게 하라"이다 `[1차, #19 부록 A.5]`.
상한 회피와 이 MVP의 보장이 같은 방향을 가리킨 흔치 않은 경우다.

**왜 규칙이 판정하는가.** 모델이 `read`라고 말해도 `1,234`는 통화를 모르면 1000배 차이의 두 해석을 갖는다.
반대로 모델이 기권해도 통화 exponent가 0이나 2면 해석은 하나로 확정된다.
**규칙이 모호성을 증명하기도 하고 해소하기도 한다** — 어느 쪽이든 모델의 확신과 무관하다.

**왜 미리 채우지 않는가.** Anthropic 측정으로 승인 프롬프트의 약 93%를 사람이 승인한다 `[1차, #19 ⑤]`.
에이전트의 값을 채워 두면 사람의 행위는 입력이 아니라 승인이 되고, 감사 로그의 `사람이 확인함`은 고무도장의 기록이 된다.
백지 입력이어야 사람의 값과 에이전트의 값이 **독립 관측**이 되고, 그래야 지표가 선다(#11).

## 결과

- 스키마가 세 배로 넓어지고 union 예산을 계산하며 설계해야 한다(설계 문서 §3.6).
- **ADR-0002가 "#18에 남아 있다"고 적은 사전 방어가 생긴다** — 백지 입력 + 확정값 재검산 + 사유 기록.
  값 원복 권한이 없는 admin의 이의 플래그는 여전히 사후 대응이고, 이 결정은 그 앞단을 메운다.
- 새로운 위험이 하나 생긴다: **false abstention**(읽을 수 있었는데 기권). `unknown` 선택지를 주면
  원래 맞힐 수 있던 것까지 기권한다는 실증이 있다 `[1차, #19 ④]`. 면제되지 않으므로 **측정 대상으로 남긴다**(설계 문서 §11.2).
- 사람에게 가는 건수가 늘어날 여지가 생긴다. 그래서 라우팅 규칙과 상한을 같은 문서에서 함께 정한다(§10) —
  표시를 1급으로 만드는 결정과 건수를 억제하는 규칙은 한 쌍이어야 한다.
- `slipscan`의 fixture·프롬프트·스키마는 재사용되지 않는다. 골격(호출 형태·이중 검증·실패 코드 구조)만 남는다.
