# ADR-0012 — 상태 전이·감사·필드 출처는 업무 DB의 한 트랜잭션에 있고, 책임자는 사람이다

- **상태**: Accepted
- **날짜**: 2026-09-22
- **맥락 티켓**: #9 (결정), #5 (결정 7 행위자/책임자), #18 (필드 출처), #10 (책임 배정), #8 (`gate=on`)

## 맥락

#9는 두 요구를 **채택 조건**으로 받았다. 감사 기록에 행위자와 책임자를 따로 남기는 것(#9 갱신, #5 결정 7),
필드 값이 어디서 왔는지를 셋으로 가르는 것(#9 갱신 3, #18)이다. 성공 기준 S11은 둘을 하드 규칙으로 잰다 —
누락 0, 책임자가 에이전트인 이벤트 0, 결재 행위의 행위자가 에이전트인 이벤트 0, 자기 결재 0(`docs/PRD.md:161`).

런타임 후보를 R-e(행위자/책임자 분리)로 재면, 플랫폼이 남기는 기록은 모두 떨어진다 —
Agent SDK OTel의 `source`는 출처 분류이지 사람이 아니고(`docs/research/agent-runtime-candidates.md:242`),
Managed Agents `user.tool_confirmation`에는 사람 actor 칸이 문서에 없고(`:529-531`, 사실 검증 6),
Temporal은 승인자 신원을 자동으로 남기지 않으며(`:644`), Inngest는 보존이 플랜에 묶이고(`:723`),
LangGraph checkpoint는 승인 감사 레코드가 아니다(`:799`).
그래서 [ADR-0011](0011-messages-api-direct-waits-are-document-state.md)은 런타임 계층을 두지 않았고, 감사는 업무 DB가 진다.
세 레인이 독립으로 같은 계약에 닿았다(비교 문서 A4·A5). 갈린 것은 비결재 조작의 책임자 규칙과 재량 관문 중의 반려였다.

## 결정

1. **감사는 업무 DB의 append-only 이벤트다.** 상태 전이·감사 이벤트·후속 작업(`job`)·outbox를 **한 트랜잭션**으로 쓴다.
   같은 `command_id`가 다시 오면 기존 결과를 돌려준다(codex §2 M).
2. **감사 이벤트는 행위자와 책임자를 따로 갖는다.** 열의 예시(이름은 구현에서 정한다):

   | 열(예시) | 제약 |
   | --- | --- |
   | `actor_kind`, `actor_id` | 조작을 실제로 한 주체. 사람·에이전트·시스템 |
   | `responsible_person_id` | **NOT NULL, 사람 참조.** 에이전트를 넣으면 커밋 거절 |
   | `document_id`, `revision`, `command_id`, `kind`, `occurred_at` | 무엇을 언제 어느 판에서 |
   | `clause_refs` | `(문서코드, 판, 조항 식별자)` 목록(ADR-0005 ④) |
   | `job_id`, `model_call_id` | 에이전트 작업과 모델 호출 기록([ADR-0016](0016-record-and-replay-model-calls.md))의 참조 |

3. **결재 4행위(승인·동의·반려·보류)의 행위자는 현재 단계 담당자인 사람이다.** 기안자의 자기 결재는 거절한다(`APV-8-2`, `docs/company/approval-matrix.md:176`).
   행위자가 에이전트인 결재 이벤트는 구조적으로 거절한다.
4. **행위자 식별자는 서버 세션에서 꺼낸다.** 요청 본문에서 받지 않는다(claude §4.1, codex §2 M "클라이언트가 보내는 이름을 그대로 믿지 않음").
5. **앱 DB 계정은 감사 행을 UPDATE·DELETE할 수 없다.** DBA까지 막는 불변 저장이라고는 주장하지 않는다(codex §5.1).
6. **플랫폼 기록(OTel·세션 이벤트·워크플로 히스토리·checkpoint)은 감사 원장으로 쓰지 않는다.**
   이 탈락은 **"플랫폼 기록을 감사 원장으로 쓸 때"에 한정**한다 — 그 플랫폼을 작업 런타임으로 쓰는 것까지 R-e로 막은 것은 아니다(claude §3.2).
7. **필드 출처는 `(entity, field, revision)` 필드 버전 행의 3값 제약이다** — `에이전트 추출` / `사람 수기 확정` / `시스템 연동`.
   덮어쓰지 않고 새 행을 만든다. 출처와 검증 수준은 다른 축이다. 검증 수준은 `CONTEXT.md:347-352`에서 출처와 따로 정의된다.
   **계산값은 네 번째 출처가 아니다.** 계산 기록(입력 revision·계산기 버전·적용 조항·달력 판·환율 근거)으로 따로 남긴다(codex §2 M).
8. **책임자 규칙은 스키마 계약까지만 정한다.** 책임자는 NOT NULL이고 사람이며, **책임자가 배정되지 않은 조작은 실행 전에 막는다.**
   추출·계산 같은 비결재 조작의 책임자를 누구로 적는지는 **#10이 정한다.** grok의 "기안자로 고정"(grok §2 가정 4)은 #10의 후보로 넘긴다.
9. **재량 관문(`gate=on`)이 열린 동안 승인·동의는 거절하고, 반려·보류는 받는다**(codex §7, grok §2 가정 5).

## 근거

**왜 한 트랜잭션인가.** S11의 "누락 0"은 상태가 바뀌었는데 감사가 없는 순간을 허용하지 않는다(codex §2 M, `docs/PRD.md:161`).
상태와 감사를 두 저장소에 쓰면 한쪽만 커밋되는 틈이 생긴다. 감사 로그의 상태 전이(`CONTEXT.md:358`)도 "추가만 되고 지워지지 않는다"다.

**왜 책임자를 지금 채우지 않는가.** codex가 짚었다 — `responsibleHumanId`를 모든 이벤트의 전결권자로 기계적으로 채우지 않는다.
수기 확정은 확정한 사람, 결재는 그 승인자, 비결재 조작은 #10의 배정 규칙을 쓴다(codex §2).
grok은 추출·계산의 책임자를 기안자로 고정하자고 했고, 그 약점도 스스로 적었다 —
"아직 확정하지 않은 오독의 책임이 출장자에게 찍힌다"(grok §10-2). 도구와 책임 배정표는 #10의 몫이라, #9는 NOT NULL과 실행 전 차단만 계약으로 둔다.

**왜 관문 중에도 반려를 받는가.** #8 결과 5는 "판단을 기록하기 전에는 승인·동의가 열리지 않는다"고 적었고 반려는 적지 않았다
(<https://github.com/DHChe/E2EAI_business_proj/issues/8#issuecomment-5769586450>). 반려까지 막으면 `APV-9-3`의 `reject_always_allowed: true`
(`docs/company/approval-matrix.md:228`)와 부딪친다(grok §10-4).

**왜 계산값을 출처로 세지 않는가.** 출처는 원사실이 어디서 왔는가이고, 계산은 그 사실들로 만든 것이다.
네 번째 값 `계산`을 더하면 원사실의 출처와 계산 계보가 한 칸에서 섞인다(codex §2 M). 계산 기록을 따로 두면 S2·S3·S10의 독립 재계산이 그 입력을 다시 읽을 수 있다
([ADR-0013](0013-postgres-object-storage-isolated-by-world-id.md)).

| 기각한 대안 | 기각 이유 |
| --- | --- |
| 플랫폼 기록(OTel `tool_decision`·`tool_confirmation`·워크플로 히스토리·Inngest 트레이스·LangGraph checkpoint)을 감사 원장으로 | 사람 두 명의 열이 없거나, 보존이 플랫폼에 묶인다(맥락의 다섯 줄). 세 레인 모두 탈락 |
| `approver` 한 칸 | 행위자와 책임자가 한 칸으로 접힌다. `CONTEXT.md:331`의 반례 "`approver` 하나로 합치지 않는다" |
| 앱 계정에 감사 UPDATE·DELETE 권한을 주고 애플리케이션 규칙으로만 지키는 안 | 버그 하나가 S11 하드 규칙을 깬다(claude §3.4) |
| 현재값만 저장·덮어쓰기 | 사람이 확정한 뒤 에이전트 값이 사라진다. `CONTEXT.md:337`은 이전 값이 감사 로그에 남는다고 적는다 |
| 건 단위 출처 태그 | 한 영수증에서 필드마다 출처가 다르다(`CONTEXT.md:338`) |
| 모의 커넥터용 네 번째 출처 | `CONTEXT.md:345` "값의 출처에 새 칸을 만들지 않는다" |
| 추출·계산의 책임자를 기안자로 고정(grok §2 가정 4) | 기각이 아니라 **#10으로 넘김**. 위 근거 |
| 관문 중 반려까지 거절 | `APV-9-3` 항상 반려와 충돌 |

## 결과

- **반증 조건.** 아래 중 하나가 관측되면 이 결정은 틀렸다.
  1. 책임자를 사람 한 명으로 적을 수 없는 적법한 이벤트가 생기고, S11의 "책임자 누락 0"과 동시에 만족시킬 수 없다(grok §8 ADR-C).
  2. #10이 구조화 값도 추출도 아닌 출처를 요구하고, `CONTEXT.md:345`의 "새 칸을 만들지 않는다"를 사람이 뒤집는다(grok §8 ADR-D).
  3. 감사 조회에서 책임자가 에이전트이거나, 결재 행위의 행위자가 에이전트이거나, 두 식별자가 한 열로 접혀 있다(grok §13).
  4. DB 제약으로 결재 행위 가드를 표현할 수 없는 결재 규칙이 생긴다(예: #17이 넣는 교차 규칙). 그러면 가드를 애플리케이션 한 층으로 줄이고 그 사실을 ADR에 적는다(claude §5.6-4).
- 결재 행위 가드를 명령 처리기에만 둘지 DB 제약으로 한 번 더 막을지는 구현 phase가 정한다. claude는 트리거로 한 번 더 막는 안을 냈다(claude §3.4).
- 수기 확정 기록은 설계 문서의 `ConfirmationEntry` 칸을 받는다(`docs/design/receipt-pipeline.md:287-305`). 그 타입에는 `actor`만 있고 책임자 칸이 없다.

  > _`docs/design/receipt-pipeline.md:287-305`의 `ConfirmationEntry`와 어긋나지만(책임자 칸이 없다), 타입만 옮기면 R-e·S11 충족을 증명하지 못한다.
  > 이 ADR은 공통 감사 envelope의 필수 책임자로 보완한다. 설계 문서는 고치지 않고 후속으로 남긴다(codex §12, grok §2 가정 3)._

- 기존 결정과의 관계.
  - [ADR-0002](0002-admin-read-only-audit-axis.md): admin에게는 값 수정·원복 명령이 없다(`docs/adr/0002-admin-read-only-audit-axis.md:25`).
    이의 플래그는 승인자 액션에 더해 세지 않는 감사자 축의 별도 명령이고(`docs/adr/0002-admin-read-only-audit-axis.md:65-66`), 그 이벤트도 행위자·책임자를 남긴다.
  - [ADR-0008](0008-extraction-uncertainty-is-first-class.md): 정책 대조는 `_status`가 없는 타입만 받는다(`docs/adr/0008-extraction-uncertainty-is-first-class.md:32`). 필드 버전 행이 그 경계의 저장 쪽이다.
  - [ADR-0009](0009-evidence-is-crop-plus-original-toggle.md): 수기 확정 때 원본을 펼쳤는지(`originalViewed`)를 감사에 남긴다(`docs/adr/0009-evidence-is-crop-plus-original-toggle.md:30`).
  - #8 결과 9는 프로토타입의 반려 자리를 비활성 "#17 대기"로 두었다.

    > _결정 9(관문 중 반려 허용)와 층이 다르다. 이 ADR은 서버가 반려 명령을 받는지를 정하고, #8 결과 9는 반려 뒤 상태가 #17 미정인 화면을 표시한 것으로 읽는다 `[유도]`.
    > 화면에 반려를 언제 열지는 이 ADR이 정하지 않는다. 두 읽기가 다르다면 다시 논의할 가치가 있다._
