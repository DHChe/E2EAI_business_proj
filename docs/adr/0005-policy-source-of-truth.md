# ADR-0005 — 규정 원문이 곧 기계 판독 원본이다

- **상태**: Accepted
- **날짜**: 2026-09-21
- **맥락 티켓**: #16 (결정·저작), #5 (선행), #13 (근거), #15 (판), #18 (경계)

## 맥락

[ADR-0004](0004-three-policy-documents.md)가 열어 둔 질문 하나는 이것이었다 —
**이 규정을 어디에 두는가. 코드 상수인가, 데이터인가, 문서인가.**

이 MVP의 차별점은 "기계 대조 가능한 **정책 원문**"이다(#13). 에이전트가 승인 카드에서
**"여비규정 제6조 제2항 때문에 한도를 넘었습니다"**라고 말할 수 있어야 하고, 그 말의 근거가
화면 밖 어딘가의 설정값이 아니라 **사람도 읽는 원문의 한 조항**이어야 한다.
그러면 저장 위치는 구현 세부가 아니라 설계다.

갈래가 셋이었다.

| 안 | 값이 사는 곳 | 사람이 읽는 것 |
| --- | --- | --- |
| ① 코드 상수 | 소스 코드 | 없음(코드를 읽어야 한다) |
| ② 데이터 파일 | YAML/JSON | 그 파일에서 뽑아 만든 화면 |
| ③ 문서 | 마크다운 | 그 문서 |

그리고 ②·③ 어느 쪽을 고르든 따라오는 두 번째 질문이 있었다 —
**사람이 읽는 산문과 기계가 인용하는 구조가 한 원본에서 나오는가, 두 벌인가.**

## 결정

**원본은 문서 셋뿐이다.** `docs/company/travel-policy.md`(`TRV`) ·
`docs/company/approval-matrix.md`(`APV`) · `docs/company/travel-procedure.md`(`PRC`).
**별도의 정책 데이터 파일을 만들지 않는다.** 값은 조항 안에 산다.

### ① 조항 식별자

`{문서코드}-{조}-{항}[-{호}]` — 예: `TRV-6-2`, `TRV-12-1`, `APV-8-1`, `PRC-3-2`.
조항 식별자는 조·항의 첫머리에 인라인 코드로 적혀 있다.

- 가지번호는 법령이 쓰는 방식(법인세법 §75의5)을 따라 `TRV-5.2-1`(제5조의2 제1항)로 적는다.
- **식별자는 재사용하지 않는다.** 조항을 없앨 때 번호를 비워 "삭제"로 남기고, 새 조항은 가지번호로 끼운다.
- 부칙은 `{문서코드}-부칙-{항}`.

### ② 값은 조항 안의 태그된 블록에만 있다

각 조항의 값은 그 조항 바로 아래 ` ```yaml ` 블록에 있고, 블록의 첫 키는 그 조항의 식별자다.

```yaml
clause: TRV-6-2      # 이 블록이 속한 조항
kind: table          # header | table | rule | enum | deadline | algorithm | reference | example
input: [지역 등급, 직급]
currency: KRW
per: 1박
values: { ... }
refs: [TRV-3-4]      # 다른 조항 참조
```

- **조항 본문은 값을 다시 적지 않는다.** 본문의 아라비아 숫자는 **조·항·호의 번호와 법령 조문 번호로만**
  쓰고, 금액·기간·개수는 "아래 블록과 같다"로 가리킨다. 세는 말을 한글로 적는 것(한 단계, 세 가지)은
  블록의 값과 어긋날 여지가 없을 때만 쓴다.
- 경계는 `lte` · `lt` · `gte` · `gt`로 적는다. "이하"와 "미만"을 산문으로만 적지 않는다.
- 키는 영문, 값의 도메인 어휘는 용어집(`CONTEXT.md`)의 한국어 용어를 그대로 쓴다.

### ③ 재량 조항을 기계가 알아본다

규정이 일부러 모호하게 남긴 조항은 블록에 표시한다.

```yaml
discretion: true
discretion_basis: 부득이한 사유        # 재량을 만드는 문구. 본문에 그대로 있어야 한다
evidence: [초과 금액, 사유, 대체안의 견적]   # 판단에 붙여야 할 것
facts_to_ask: [대체안을 쓰지 않은 이유]      # 물어볼 사실
decided_by: 결재권자                      # 판단 책임자
must_not_auto_decide: [부득이한 사유의 인정]  # 금지된 자동 확정
```

에이전트는 `discretion: true`인 조항을 스스로 확정하지 않고, `facts_to_ask`를 묻고 `evidence`를 모아
`decided_by`에게 올린다. `must_not_auto_decide`에 적힌 것은 에이전트가 어떤 경우에도 값으로 정하지 않는다.
뒤의 세 칸은 2026-09-21 교차 대조 결정(D-5)으로 더했다 — 재량 조항은 넷(`TRV-7-1` · `TRV-12-1` · `TRV-13-4` · `PRC-13-5`)이고,
네 블록 모두 이 세 칸을 갖는다.

### ④ 판(版)은 문서 단위와 조항 단위 둘 다다

- 문서 머리 블록이 `edition`과 `effective_from`을 갖는다.
- **외부 규범을 참조하는 조항은 조항 단위로 판을 갖는다**(`TRV-15-2`).
- 하나의 출장에 어느 판을 적용하는지는 `PRC-2-2`가 정한다 — 사전승인 기안일 기준.
- 판정 기록에는 **(문서코드, 판, 조항 식별자)** 세 값을 함께 남긴다.

### ⑤ 파생물은 저장소에 두지 않는다

블록을 모아 만든 JSON은 **추출 결과**이지 원본이 아니다. 손으로 고치지 않고, 저장소에 커밋하지 않는다.
추출기와 아래 ⑥의 검사기는 `/harness` phase에서 구현한다.

### ⑥ 검사 규칙

| # | 규칙 |
| --- | --- |
| L1 | 모든 `yaml` 블록에 `clause`가 있고, 그 값이 블록을 품은 조항의 식별자와 같다 |
| L2 | 조항 식별자는 문서 안에서 유일하다 |
| L3 | `refs`의 모든 식별자가 실재한다(문서 사이 참조 포함) |
| L4 | 조항 본문의 아라비아 숫자가 조·항·호 번호와 법령 조문 번호뿐이다 |
| L5 | `discretion: true`인 블록은 `discretion_basis`를 갖고, 그 문구가 본문에 그대로 있다. `facts_to_ask` · `decided_by` · `must_not_auto_decide`도 갖는다 |
| L6 | 문서 머리 블록에 `edition`과 `effective_from`이 있다 |
| L7 | `kind: example` 블록의 기대값이 규칙을 실제로 적용한 결과와 같다 |

**L7이 이 결정의 핵심 장치다.** 예시가 시험 벡터이므로, 규칙을 고치고 예시를 고치지 않으면 검사가 깨진다.

### ⑦ 인용과 표시

에이전트는 **`여비규정 제6조 제2항(TRV-6-2)`** 형식으로 인용한다.
승인 카드에 올리는 근거 문구는 그 조항의 본문과 블록을 **원문에서 그대로** 가져온다. 다시 쓰지 않는다.

### ⑧ 저작 노트는 조항이 아니다

각 문서 끝의 `저작 노트` 절은 왜 그렇게 저작했는지의 기록이고 **규범이 아니다.**
인용 대상이 아니며 L4의 적용을 받지 않는다.

## 근거

### 코드 상수를 버린 이유

한도를 코드에 두면 판정 근거가 **조항이 아니라 소스 코드의 줄**이 된다. 에이전트가 "제6조 제2항 때문"이라고
말하려면 그 조항이 실재해야 하는데, 코드 상수에는 조항이 없다. 한도를 고치는 일이 배포가 되고,
사람이 규정을 읽으려면 코드를 읽어야 한다. ADR-0004가 기한을 세 번째 규정으로 끌어올린 이유가
**"근거가 제○조 제○항이 아니라 시스템 설정값이 되는 것"**을 막기 위해서였는데, 코드 상수는 같은 실패다.

### 문서 없이 데이터만 두는 안(②)을 버린 이유

②는 값의 구조가 깔끔하지만 **사람이 읽는 것이 원본이 아니게 된다.** 심사자·감사자·결재권자가 보는 화면은
데이터에서 생성된 표현이고, "규정 원문"이라 부를 물건이 저장소에 없다. 게다가 산문을 YAML 문자열 안에
쓰게 되어 저작과 검토가 둘 다 나빠진다. 이 map은 제품 코드를 쓰지 않으므로 **생성기가 없으면 마크다운도 없다** —
지금 당장 원본이 없다는 뜻이다.

### 두 벌(문서 + 별도 데이터 파일)을 버린 이유

가장 흔한 선택이고, 가장 위험한 선택이다. 같은 숫자를 두 곳에 적으면 **언젠가 어긋난다.**
ADR-0004가 네 번째 규정(법인카드 사용지침)을 버린 논리가 그대로 적용된다 —
**"네 원문이 서로 모순되는 것이 하나가 없는 것보다 나쁘다."** 어긋난 두 원문은 어느 쪽이 참인지
판정할 방법이 없고, 그 상태에서 에이전트가 인용하면 **틀린 근거를 확신에 차서 제시한다.**

동기화 검사를 붙여 두 벌을 유지하는 방법도 있지만, 검사가 잡아 주는 것은 **형태가 같은 값**뿐이다.
표에 없는 조항이 산문에만 생기거나, 산문의 단서("다만 …")가 데이터에 반영되지 않는 어긋남은 잡히지 않는다.

### 마크다운 표가 아니라 YAML 블록인 이유

마크다운 표가 사람에게는 더 읽기 좋다. 그러나 표의 칸은 **타입도 단위도 경계 의미도 담지 못한다.**
`150,000원`이 정수인지 문자열인지, `이하`인지 `미만`인지, 통화가 무엇인지가 표에는 없다.
#19가 확인한 대로 로캘에 따라 `1.234,56`이 실재하므로 숫자 표기를 파서의 추측에 맡길 수 없다.
YAML 블록은 그 셋을 명시하고, 렌더링된 화면에서도 코드 블록으로 그대로 보인다 —
**기계가 읽는 원문이라는 사실이 화면에 드러나는 것**은 이 MVP에서 비용이 아니라 이득이다.

### 조항 본문에 수치를 쓰지 않는 이유

한 조항 안에서도 산문과 블록이 어긋날 수 있다. "10영업일"이 본문에 있고 블록에 `9`가 있으면
두 벌 문제가 조항 단위로 재현된다. 수치를 블록에만 두면 **어긋날 두 번째 자리가 아예 없다.**
대가는 본문이 "아래 블록과 같다"를 반복한다는 것인데, 블록이 바로 다음 줄에 있으므로 읽는 데 지장이 없다.

## 결과

- **규정 셋이 이 저장소의 정책 원본이고, 다른 곳에는 정책 값이 없다.** 새 값이 필요하면 조항을 만든다.
- 판정 기록이 `(문서코드, 판, 조항 식별자)`를 남기므로, 나중에 규정이 바뀌어도 **그때 무엇을 근거로 판정했는지**
  재구성할 수 있다. `PRC-2-2`가 적용 판을 사전승인 기안일로 고정한 것이 그 재구성을 가능하게 한다.
- **재무합의의 세 성질(순차·차단·항상 반려 허용)이 사는 자리가 정해졌다** — `APV-9-3`이다.
  [ADR-0001](0001-approval-semantics-per-term.md)이 "드러난 설정값"이라고 한 그 값이 조항 값이 된다.
  다만 ~~**노출의 형태와 변경 주체는 여전히 #9·#10의 몫이다.**~~ 이 ADR은 값이 어디 저장되는지만 정했다. **정정(#23, 2026-09-22)**: 노출의 형태와 변경 주체는 [ADR-0014](0014-apv-9-3-exposed-declaratively.md)가 정했다 — 화면은 판 1의 세 값을 `(APV, 판, APV-9-3)` 인용과 함께 읽기 전용으로 표시하고, 값은 규정 개정권자가 새 판을 게시해야만 바뀐다. 개정권자의 직책은 #10에 남는다.
  규정을 개정할 권한이 곧 그 설정을 바꿀 권한이 되므로, 두 결정이 만나는 지점이 생겼다.
- 비용 셋. ⑴ 사람이 YAML을 읽어야 한다. ⑵ 추출기와 검사기를 만들어야 하고, 만들기 전까지 L1~L7은
  사람이 지킨다. ⑶ 조항을 옮기거나 합치는 리팩터링이 비싸진다 — 식별자를 재사용하지 않기로 했으므로
  번호가 시간이 갈수록 성기어진다. 법령이 실제로 그렇게 늙는다는 점에서 받아들일 만한 비용이다.
