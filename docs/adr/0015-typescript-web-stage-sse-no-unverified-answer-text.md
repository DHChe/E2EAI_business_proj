# ADR-0015 — 웹은 TypeScript 단일 언어이고, 진행은 단계 이벤트 SSE로 보내며, 검증 전 답변 문장은 화면에 내보내지 않는다

- **상태**: Accepted
- **날짜**: 2026-09-22
- **맥락 티켓**: #9 (결정), #8 (상호작용 모델), #12 (시각 시스템), #18 (설계 문서의 TS 블록)

## 맥락

#9의 판단 기준은 상호작용 모델이 요구하는 것이다 — 진행 상황 스트리밍, 승인 대기의 표현, 여러 작업의 동시 표시, 중단과 재개(#9 Question).
#8은 척추를 **기한순 평평한 승인자 큐**로 정했다. 한 화면이 여러 문서의 상태를 동시에 읽는다.

세 레인은 TypeScript · React(Vite) SPA · Node API · SSE(명령은 POST)에 독립으로 닿았다(비교 문서 A6).
갈린 것은 둘이다. 웹 서버(codex Fastify, grok·claude Hono)와, **보류 답변을 만드는 동안 무엇을 화면에 흘리는가**였다.

- codex: 모델 토큰은 임시 미리보기로만, 주 화면에는 확정 단계를 보인다(codex §4).
- grok: 생성 중 토큰을 진행 표시로 흘리고, 규칙 검사를 통과한 뒤 카드에 고정한다(grok §4.1).
- claude: **토큰을 흘리지 않는다.** 단계 전이만 보낸다(claude §3.1).

## 결정

1. **TypeScript 단일 언어다.** React(Vite) SPA · Node API · 워커 · 상태 리듀서를 같은 언어로 쓴다.
2. **웹 서버는 Hono다.** Fastify는 동등한 대안이고 되돌리기 쉬워 따로 ADR로 올리지 않는다.
3. **명령은 `POST`로 받고, 진행은 SSE로 보낸다.** SSE 이벤트의 `id`는 영속 순번·cursor다. 재접속하면 snapshot + cursor로 이어 받는다.
   한 연결이 그 뷰어의 큐 전체를 받는다. SSE가 막히면 폴링으로 내려가고, 연결 상태를 표시한다.
4. **R-a(진행 스트리밍)는 "단계 전이가 새로고침 없이 도착하는 것"으로 정의한다.** 토큰 단위 스트리밍은 요구하지 않는다.
5. **보류 답변은 토큰을 스트리밍하지 않는다.** 화면에는 단계(작성 중 → 인용·숫자 검사 중 → 완료)만 SSE로 보내고, **검사를 통과한 완성 문장만** 표시한다.
6. **설계 문서의 TS 블록은 언어를 구속하지 않지만, 이 결정은 TS로 기운다.** 구속하는 것은 모양이다 — `Confirmed<T>`에 `_status`가 없다는 것, 수기 확정 감사의 칸.
   정적 타입만 믿지 않고 API·모델·DB 입력 경계에서 런타임 검증한다(codex §4).
7. **Python으로만 돌릴 수 있는 부품이 들어오면 스택을 바꾸지 않고 `job`의 한 종류로 Python 사이드카를 붙인다**(claude §4.4-1). 1순위 후보는 방향 분류기다.

## 근거

**왜 TypeScript인가.** 설계 문서의 TS는 "설계를 못박기 위한 버리는 코드"다(`docs/design/receipt-pipeline.md:6`). 법적으로 묶지 않는다(codex §4, grok §7, claude §4.2).
그래도 그 블록들은 저장소에서 가장 정밀한 타입 명세다. 설계 문서에 TS 블록이 21개 있고(`grep -c '^```ts' docs/design/receipt-pipeline.md` = 21),
zod 슬롯(`docs/design/receipt-pipeline.md:373-442`)은 구조화 출력의 스키마로 그대로 들어간다(claude §4.2). 리듀서를 서버와 화면(버튼 활성 조건)이 같은 코드로 쓴다(claude §4.2 W1 R-f).
Python으로 가면 명세가 둘이 되거나 생성기가 하나 는다 — "묶지는 않지만 강하게 기운다"(claude §4.2).

**왜 Hono인가.** 두 레인(grok·claude)이 골랐고 codex의 Fastify와 R-a~R-g에서 갈리지 않는다. 2:1로 정하고, 바꾸는 비용이 작다는 것을 이 ADR에 적어 둔다.

**왜 SSE이고 cursor는 영속인가.** 서버→브라우저 한 방향이면 충분하고, 명령은 `POST`로 받으니 양방향이 필요 없다(claude §4.3).
SSE의 `id`/`Last-Event-ID`는 재연결의 표준 수단일 뿐이고 서버의 이력 보존·재생까지 주지 않는다(codex §4, 레인이 인용한 WHATWG SSE 명세, 확인 2026-09-22).
그래서 cursor는 DB의 영속 순번이어야 한다. PostgreSQL에서는 순번을 할당한 순서가 커밋 순서라고 가정하지 않고, outbox 배포자가 확정한 순서로 cursor를 준다(codex §4).
이력 범위 밖 cursor는 전체 snapshot 재조회로 회복한다(codex §4).

**왜 보류 답변을 흘리지 않는가.** 보류 답변은 카드와 같은 규율을 따른다 — 숫자는 계산 기록에서만, 근거는 조항 원문 인용으로(`docs/PRD.md:45`).
S4는 인용이 조항 원문의 연속 부분문자열인지, 숫자가 계산 기록과 같은지를 기계 대조하고 위반 0을 요구한다(`docs/PRD.md:154`).
제외 13은 판정 권고를 두지 않는다(`docs/PRD.md:141`). 검증 전 문장이 **잠깐이라도** 보이면 S4를 어긴 문장이나 권고를 화면에 실은 것과 같다(claude §3.1).
"미리보기"라는 표시를 붙여도 사람이 읽은 뒤다. 그래서 R-a를 단계 전이로 정의했다(결정 4).

| 기각한 대안 | 기각 이유 |
| --- | --- |
| 보류 답변 토큰을 미리보기로 흘리고 검사 뒤 고정(grok §4.1, codex §4) | 위 근거 — 검사 전 문장이 화면에 한 번은 보인다 |
| 문장 단위로 검사한 뒤 흘림(코디네이터 절충안) | 사용자가 고르지 않았다(결정 기록 U7). 결정 기록은 이 안만의 기각 이유를 따로 적지 않았다 |
| WebSocket | 양방향이 필요 없다(claude §4.3). 며칠짜리 대기를 연결로 붙들면 끊김이 대기 소실이 된다(grok §4.2) |
| 폴링만 | 상태 갱신은 되지만 R-a가 줄어든다(codex §4 표). 폴링은 SSE가 막혔을 때의 대체 경로로만 둔다 |
| Next.js on Vercel(서버리스) | Fluid compute의 Node.js/Bun/Python 기준으로 함수 최대 실행 시간이 Hobby 300초, Pro·Enterprise 기본 300초·일반 최대 800초·확장 최대 1800초 베타(함수별 설정)이고 스트리밍 응답 시간도 포함된다 `[1차]` — <https://vercel.com/docs/functions/limitations#max-duration>(사실 검증 9, 확인 2026-09-22). 같은 프로세스에 워커를 둘 수 없어 [ADR-0011](0011-messages-api-direct-waits-are-document-state.md)의 질문이 다시 열린다(claude §4.2 W2) |
| Next.js + 별도 worker(codex가 "가능"으로 적음) | R-a~R-g는 충족한다. SSR 요구가 없고 별도 worker 조건에서 웹까지 한 요청 실행 모델로 묶는 이득이 작다(codex §4) |
| FastAPI + React | 타입 명세가 두 벌이 되고 리듀서가 Python과 TS 화면 조건으로 갈린다(claude §4.2 W3) |
| Hono 서버 렌더링 + htmx | 차점이다. 크롭·원본 토글(ADR-0009)처럼 클라이언트 상태가 있는 부품이 있다. 차이는 되돌릴 수 있는 크기다(claude §4.2) |
| 브라우저가 Claude를 직접 부르고 상태를 가짐 | 신뢰할 서버 귀속·감사가 없다 — R-e 탈락(codex §4 표) |

## 결과

- **반증 조건.** 아래 중 하나가 관측되면 이 결정은 틀렸다.
  1. 실제 대상 브라우저·프록시에서 SSE 재연결 뒤 목록과 상세의 revision이 어긋나거나 상태 변화가 유실된다. 그 스트림 구현은 부적합하다(codex §4).
  2. 배포 플랫폼의 프록시가 SSE를 버퍼링하거나 끊는다. 그러면 폴링으로 내려간다 — 배포 뒤 첫 확인 항목이다(claude §4.4-2).
  3. 보류 답변이 몇 턴의 루프로는 S4·S5 위반을 막지 못해 탐색이 길어지고, 한 번의 답변이 수십 초를 넘는다(실측). 그래도 토큰은 흘리지 않고, R-a를 "도구 호출 단위 진행"으로 올린다(claude §3.6-2).
  4. #12의 시각 시스템이 특정 프레임워크에 묶인 부품 라이브러리를 요구한다. 그러면 React 선택을 다시 본다(claude §4.4-3).
- `docs/ui-guide.md:22-23`은 색상 토큰·컴포넌트 스펙을 "기술 스택이 정해진 뒤" 적는다고 했다. 이 ADR로 #12가 그 자리를 채울 수 있다. CSS 방식과 부품 라이브러리는 정하지 않는다.
- 방향 분류기의 실행 자산에는 공백이 있다. 저자 측 HF 저장소에 12-class 가중치 `weights.zip`이 공개돼 있지만(<https://huggingface.co/datasets/krutrim-ai-labs/ocr_rotation_bench>),
  설계가 전제한 4-class 체크포인트와 실행 코드의 공개는 확인하지 못했고 라이선스는 Krutrim Community License다(사실 검증 3).
  이것은 모순이 아니라 **설계 채택과 실행 자산 검증 사이의 공백**이고, ~~#18 후속·#10으로 넘긴다.~~ **정정(#10, 2026-09-22)**: #10은 4-class 가중치를 지금 채택하지 않고 사이드카 자리만 유지한다. 자산 검증은 #18 후속이다. 방향은 EXIF만 쓰고, EXIF가 없으면 `방향 미보정`을 기록한 채 진행한다(`docs/research/agent-architecture-comparison.md:60` A13, `:194` C4, `docs/ARCHITECTURE.md` §10). 사이드카의 자리만 이 ADR이 남긴다.
