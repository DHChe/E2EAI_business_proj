# #17 상태 어휘 — 3레인 통합 비교와 결정 기록

- **날짜**: 2026-09-22
- **맥락 티켓**: #17 (반려의 후속 상태 정의 — 상태 어휘 전체의 주인)
- **상태**: 비교와 결정 완료. 결정은 ADR 0023–0028(`docs/adr/0023`–`0028`)과 `docs/ARCHITECTURE.md` §5·§7, `CONTEXT.md`로 옮겼다(§7).

이 문서는 세 레인의 독립 제안을 한 자리에 놓는다. 무엇이 합의였고 무엇이 갈렸으며, 누가 어떻게 정했는지를 남긴다. 여기의 번호(A·D·U·C)는 뒤에 쓸 ADR과 상태 문서가 그대로 인용한다.

## 0. 방법

1. **세 레인 독립 제안.** codex·grok·claude 세 모델이 **같은 지시서**(레인 이름만 다름)로 서로 읽지 않고 풀었다. 셋 다 develop `47c89dc`에서 갈라졌다. codex·grok은 Orca 워커로(run `run_b792268de1a8`), claude는 코디네이터의 서브에이전트로 돌았다.

   | 레인 | 커밋 | 분량 | 원문 브랜치 (origin에 push함) |
   | --- | --- | --- | --- |
   | codex | `6d31ea4` | 447줄 | `DHChe/frontier-17-states-codex` |
   | grok | `2bd019f` | 539줄 | `DHChe/frontier-17-states-grok` |
   | claude | `cdfb1a9` | 773줄 | `DHChe/frontier-17-states-claude` |

   원문은 `docs/research/state-vocabulary-proposal-<레인>.md` 한 파일씩이고, develop에 병합하지 않고 위 브랜치로만 보존한다(§7-4). 이 문서는 원문을 "codex §5.1"처럼 절 번호로 가리킨다. grok의 번호 없는 절은 이름으로 적었다(상태 표·전이 표·규정표·ADR 후보·U1–U4·경계·모순).
2. **1차 비교는 비교자 서브에이전트가 했고, 결정을 가르는 사실은 코디네이터가 원문으로 재확인했다.** 비교자는 모든 인용을 레인 원문과 대조했고(굵게 표시 `**`만 뺐다), 저장소 줄은 develop `47c89dc`에서 확인했다(§4의 ✔). 코디네이터는 핵심 인용 9개와 `PRC-9-2`(travel-procedure.md:158)·PRD:133의 충돌을 원문으로 다시 봤다. 저자와 다른 모델의 교차 검증은 아직이다(§7-2).
3. **결정.** 세 레인이 독립으로 같은 답을 낸 16건은 합의로 받았다(§2). 갈린 자리 가운데 되돌리기 어려운 6건은 사용자가 골랐고, 여섯 모두 코디네이터 추천과 같다(§5). 되돌리기 쉽거나 합의가 받치는 10건은 코디네이터가 정해 사용자에게 알렸다(§6, 이의 없음).

출처 표기: **합의** = 세 레인이 서로 읽지 않고 같은 답. **사용자** = 사용자가 고름. **코디네이터** = 코디네이터가 정하고 사용자에게 알림. `[코디네이터 판단]` = 레인 주장이 아니라 비교하는 쪽의 해석. 인용 “…”은 해당 레인 원문 그대로다.

## 3. 갈린 자리

### D1. 축의 연결 — 누가 되돌림을 일으키고, 지급·반환은 어느 축에 있나 → C8, U6
- codex §2 “명령 처리기가 변경 사실을 수락하면서 다음 셋을 원자적으로 정한다” — 되돌림은 system의 변경 수락이 정한다. 지급·반환은 결재와 별도인 집행 기록이다(§6).
- grok §5 “행위자는 짝을 닫거나 값을 고친 사람이다.” — 복귀는 사람(person)의 명령 `판정입력 변경으로 첫 단계 복귀`다. `지급 처리됨`은 문서 상태다.
- claude §6.1 “행위자는 시스템이고, 책임자는 결재선 계산에 배정된 업무 운영 담당자다” — system 사건 `카드 변경`·`결재선 변경 회송`. `지급 처리됨`·`반환 대기`는 문서 상태다.
- 실질 차이: 되돌림의 `actor_kind`(system 대 person)와 책임자, 지급·반환 상태가 놓이는 축. 이름만 다른 것: "재개 판정표"·"복귀 명령"·"카드 차이 규칙". 되돌리는 범위의 차이는 D7에서 다룬다.
- 되돌리기: 어렵다. 감사 이벤트의 행위자·책임자 열(ADR-0012:29-31)과 상태 스키마에 걸린다.

### D2. 반려의 결과 — 재상신 시작점, 결재선 재계산, 앞선 승인의 효력 → U1, C1
- codex §3 “반려된 시도의 중간 승인은 이력만 남고 새 시도에 승계하지 않음”, 결재선은 “사람의 재상신 때 당시 조직 정보와 수정 입력으로 다시 계산; 첫 결재권자부터”.
- grok §1 “재상신은 결재선 구성원을 다시 계산하지 않고 첫 단계부터 다시 받는다.” — 선이 바뀌면 `재기안` → `기안`, 조직 정보는 재기안 시점.
- claude §10 ADR-0025 “재기안은 같은 문서 ID의 새 기안 차수이고 결재선은 새 기안 시점에 다시 계산한다.” §9 R2 “다시 계산한 결재선의 같은 단계에 같은 사람이 서고 그 사람에게 제시되는 판정 자료가 달라지지 않았으면, 그 단계의 앞선 승인(동의)은 유지된다.”
- 실질 차이: ① 앞선 승인 — codex·grok은 하나도 잇지 않고, claude는 카드가 안 바뀐 단계를 유지한다(§11 A로 사용자에게 물음). ② 재상신 뒤 시작점 — codex·grok은 첫 단계, claude는 카드 차이로 정한 가장 앞 단계. ③ 선 재계산 — codex·claude는 재상신 때 다시 계산한다. grok은 고정 선을 쓰되 가드에서 `APV-8` 계산값과 비교하므로(전이 표) 선이 달라지면 결국 재기안이 된다. 셋 다 새 문서가 아니라 같은 문서의 새 시도·revision·차수다.
- 이름만 다른 것: 반려 뒤 상태의 이름 `반려`(codex·grok) 대 `재기안 대기`(claude). "재기안"의 뜻도 다르다 — codex는 반려 뒤 새 시도 전체, grok은 선이 바뀌는 수정만 가리킨다.
- 스스로 적은 약점: codex §15 “반려와 보류의 경계가 분명하지만 반려 오용 비용이 크다”, grok §1 반증 “첫 단계 재시작은 확인이 아니라 같은 클릭의 반복이다.”, claude §11 A “S15(카드 완전성)에 전적으로 기댄다.”
- 되돌리기: 어렵다. 승인 이벤트를 revision·카드에 묶는 방식(감사 스키마)과 규정 `APV-11-3` 초안(codex·claude)에 걸린다.

### D3. 끝내는 길 — 철회·취하·종결 → U2
- codex §3 “사전승인 반려 뒤 기안자가 더 진행하지 않으면 `반려`를 종결 이력으로 남긴다” — 명시적 종결 명령은 없다. 정산 반려를 그대로 두는 경우는 언급이 없다.
- grok §1 “`취하`의 도착만 종결 상태 `취하`다.” — 두 문서 모두에 적용된다. U1은 취하가 출장 취소는 아니라고 추천한다.
- claude §15 “사전승인만. 기안자가 재기안하지 않고 닫은 문서. 출장 취소로 본다” — 정산 철회는 `WITHDRAW_NOT_ALLOWED`로 거절한다(§18).
- 실질 차이: 정산을 닫을 수 있는가(grok 예, claude 아니오, codex 언급 없음). 문서를 닫으면 출장도 취소인가(claude 예, grok 아니오, codex는 "출장 미실시 표시는 사건의 사실 기록일 뿐"이라고 적음).
- 스스로 적은 약점: grok U1 “큐와 조회에 "문서가 없는 출장"이 남고”, claude §11 E “중복 기안 같은 사고를 닫을 길이 없다”. codex는 언급 없음.
- 되돌리기: 어렵다. 종결 상태를 더하거나 빼는 일은 상태 기계, 감사 이벤트, S10의 닫는 사건에 걸린다.

### D4. 답 없는 보류와 기한 경과 → U3, C2
- codex §4 “기한 경과를 한 번 기록해 담당자·기안자·배정된 절차 운영 담당의 지연 목록에 올린다” — system 명령 `DeadlineElapsed + EscalationRecorded`, 책임자는 인사 절차 운영 담당(미배정이면 `RESPONSIBLE_UNASSIGNED`). 보류 응답 기한은 #20이 블록 값을 정한 뒤에만 둔다(PRC-14.3-1).
- grok §2 “기한 경과는 계산해서 문서에 표시한다. 상태 전이가 아니다.” — 경과할 때마다 감사 이벤트를 남기는 안은 기각했다. 답변 전용 기한도 만들지 않는다.
- claude §9 R9 “이 기한이 지나면 그다음 영업일을 그 결재자의 새 도달일로 본다.” — 답변 기한을 신설하고(§11 F 추천 3영업일) 계산값으로 둔다. §4는 “보류 중인 승인자가 답을 기다리지 않고 바로 결정할 수 있게 한다”.
- 보류에서 바로 나가는 결재 행위: codex는 반려만(§6·§7), grok은 전이 표에 행이 없다(§2 반증 문장은 결재자의 반려를 언급한다), claude는 승인·동의·반려(§16).
- 실질 차이: 경과를 영속 사건과 책임자로 둘지(codex), 계산으로만 둘지(grok·claude). 새 시계를 둘지(claude), 두지 않을지(grok), #20 조건부로 둘지(codex).
- 스스로 적은 약점: codex §15 “청구·비용을 침묵으로 없애지 않지만 열린 문서가 누적된다”, grok U3 “답 없는 보류가 문서 기한보다 길게 남을 수 있고”, claude §11 F “출장 중인 기안자에게 짧을 수 있다”.
- 되돌리기: codex안이 가장 어렵다. ARCH:298-305(기한을 저장하지 않고 표시만 함, 자동 전이가 생기면 책임자 행)를 고쳐야 하고 스케줄러 명령이 필요하다(codex §13이 스스로 적음). claude안은 규정 신설(R9)과 보류의 출구 전이 추가라 중간이다. grok안은 나중에 더하기만 하면 된다.

### D5. 정산 재심 — 복귀 단계, 완료 효력, 재대사 → U4
- codex §5.1 “정산은 기존대로 재무합의대기로 보내되, 복귀점과 원 승인·지급 이력을 보존한다” — 결재권자 범위의 쟁점이 있으면 원 결재선까지 본다. 무변경 완료 건은 원 `완료`로 돌아간다. 정정이 있으면 차액만 처리한다.
- grok §3 “재심이 끝난 뒤 저장해 둔 옛 단계로 점프하지 않는다.” “새 `완료`는 전결권자의 새 승인이다” — 두 번째 지급은 자동으로 열지 않고 `재정산 필요` 표지만 둔다. “플래그 자체는 값을 바꾸지 않으므로 대사를 다시 돌리지 않는다.”
- claude §9 R12 “질문이 제1항의 사항이면 재무합의자가, 그 밖의 사항이거나 사전승인 문서이면 전결권자가 다시 본다” — 유지로 닫히면 “원래 완료 시각과 기존 승인이 그대로 효력을 가진다”. 플래그를 열 때 “현재의 카드 청구 줄로 대사를 한 번 다시 계산”한다.
- 재무합의 0명(`APV-9-4`) 정산: codex는 `UNDEFINED_BY_17`로 계속 거절, grok은 `결재대기` 1단계, claude는 언급 없음.
- 실질 차이: 무변경 재심을 누가 다시 보나(codex는 재무 k명에 결재권자 쟁점이면 +n, grok은 선 전체, claude는 영역별 한 단계). 완료 시각을 유지하나(codex·claude) 새로 만드나(grok — 지급 기한 기준일(`PRC-16-1`, travel-procedure.md:295)에 미치는 영향은 grok에 언급 없음). 재대사는 codex가 정정 때, grok이 값이 바뀔 때만, claude가 늘.
- 스스로 적은 약점: codex §15 “이중 지급 방지에 유리하나 재심 지연을 직원이 부담한다”, grok U2 “재심이 길어지면 지급 기한 표시가 쌓인다”, claude §11 B “두 영역에 걸친 질문의 처리가 규칙 하나 더 필요하다”.
- 되돌리기: 어렵다. ADR-0002 개정의 범위, 지급 기한 기준일, 감사 이벤트에 걸린다.

### D6. 사전승인 재심의 대상 → U5, C7
- codex §5.1 “진행 중에는 원 현재 결재권자, 완료 건은 원 전결권자의 `결재대기(재심)`로 보내는 것을 추천한다” — 개정 수락 전에는 거절을 유지한다. 완료 뒤의 수정은 새 재기안이 아니라 PRC-9대로 정산에 연결한다.
- grok ADR-0026 “사전승인과 재무합의자가 0명인 정산의 도착은 `결재대기` 1단계다.”
- claude ADR-0027 “판단 영역과 모든 사전승인은 전결권자 단계” — 재심 반려 뒤 위약금은 회사가 부담한다는 R4 초안을 짝으로 둔다.
- 실질 차이: 첫 결재권자(grok) 대 전결권자(codex 완료 건·claude). 재심이 반려로 닫힐 때 grok·claude는 보통의 반려 → 재상신 경로를 탄다. codex는 완료 건의 수정에 재기안을 쓰지 않고, 원 결정의 효력 취소는 규정 개정까지 미정으로 둔다(§5.1-6).
- 한 레인만 적은 충돌: 완료된 사전승인의 재심은 PRC-9-2·PRD:133과 긴장한다(§4 1번). grok·claude의 경로도 같은 자리에 걸린다 `[코디네이터 판단]`.
- 스스로 적은 약점: codex §15 “PRC-9의 두 봉우리 경계와 충돌 소지가 있어”. grok §3 반증은 결재권자가 재무 증빙 없이 판단 못 하는 경우, claude §5 틀리는 조건은 전결권자 본인의 판단이 쟁점인 경우다.
- 되돌리기: 어렵다. ADR-0002 개정과 규정 예외 문언이 필요하다.

### D7. 값 수정·짝 보류 해소 뒤의 재개 → U1, C5
- codex §5 “값이 그대로면 같은 단계, 판단 입력이 달라지면 동일 결재선의 처음, 결재선이 달라지는 수정은 재기안이다”
- grok §5 “명령 `판정입력 변경으로 첫 단계 복귀`가 문서를 첫 단계로 보낸다.” 선이 바뀌면 “가드 `재기안 필요`가 승인·동의를 `LINE_CHANGE_REQUIRES_REDRAFT`로 거절한다.”
- claude §7 “바뀌었으면 → 바뀐 가장 앞 단계로 돌아가고 그 단계와 뒤의 승인은 실효.” 선이 바뀌면 system이 `재기안 대기`로 회송한다(§16).
- 비교 범위: codex는 승인 카드가 판단 근거로 제시한 스냅샷 전체(증빙·짝·법정 판정·정책 결과·재량 판단·목적·사유), grok은 총액·한도 적용 금액·상향 사유·차이 목록 넷, claude는 S15 판정 기록에서 기한 표시를 뺀 것.
- 상신 뒤 기안자가 고칠 수 있는 창구: grok은 `기안`·`반려`·기안자 대상 `보류`에서만(§4.1), claude는 보류 답변·배정된 짝 확인·배정된 수기 확정 셋이고 폼 항목은 반려 → 재기안(§6.1). codex는 명시하지 않았다(전이 표의 "수정 허용 상태").
- 완료와 겹치거나 완료 뒤에 생긴 짝 변동: codex는 선행 사건 하나만 받고 완료 뒤는 재심으로만, claude는 “문서 상태는 그대로이고 "완료 후 대사 변동"으로 표시한다”, grok은 언급 없음.
- `[코디네이터 판단]` codex·grok에는 "재기안 필요"가 된 진행 중 문서를 기안자에게 돌리는 행이 반려 말고는 없다(grok 전이 표에서 `재기안`의 출발은 `반려`·`기안`뿐이고, codex §6은 `재기안 필요`를 상태 옆 표시로 둔다). 그러면 현재 승인자의 반려 클릭이 필요하다. claude §8의 −1이 없애려는 것이 바로 이 클릭이다.
- 스스로 적은 약점: codex §15 “사소한 근거 수정에도 반복 접촉이 든다”. grok §5 반증은 같은 본문을 매번 다시 승인하는 경우, claude §7 반증은 사실상 늘 처음부터가 되는 경우다.
- 되돌리기: 어렵다. 승인 실효 이벤트(claude `approval.lapsed`), 스냅샷 비교 범위, 복귀 명령의 행위자에 걸린다.

### D8. 항목별 부분 승인 대 재량 "인정하지 않음" — 결론은 같고 설명이 다르다 → C9
- codex §5.2 “결과 금액이 갈라진다는 점에서 같고, 미결 항목을 남긴다는 점에서 다르다”, grok §4.2 “재량 "인정하지 않음"은 이와 다른 문제다.”, claude §6.2 “같은 문제가 아니다.”
- 실질 차이는 작다. 재량 조항이 없는 항목을 인정하지 않으려면 claude는 반려라고 하고, codex도 “`PRC-13-5`에서 근거가 없으면 반려하라는 규정을 항목 0원 처리로 우회하지 않는다”(§5.2)고 적어 같은 방향이다. grok은 언급이 없다. 거부 이름을 둔 것은 grok뿐이다. claude만 ADR-0003의 provisional 표지를 떼자고 한다(ADR-0028).
- 스스로 적은 약점: codex §15 “직원은 정상 금액도 기다린다”. grok §4.2 반증은 지급 기한을 넘기는 일이 반복되는 경우, claude §6.2 반증은 재량 조항 없는 불인정 반려가 다수인 경우다.
- 되돌리기: 쉽다. 세 레인이 같은 방향이다. provisional 표지를 떼는 일만 ADR이다.

### D9. 사람 확인 지점을 세는 법 — 결정 없음, 수치는 #11로
- codex §9 “정상 경로 순증 0, 예외 진입 경로 2개(사전승인 재심·반환 종결), 새로운 승인자 역할 0”, grok §6 “새로 생기는 사람 행위는 +1, 기안자의 `취하`다.”, claude §1 “타임아웃에는 하나도 더하지 않는다.”(§8은 −3/+3).
- 같은 사실을 다르게 센 곳: 사전승인 재심(codex +1 경로, claude +2, grok은 "새 역할이 아니다"), 반환(codex +1 경로·집행 동작 순증 0, claude +3, grok은 "새 자리가 아니다"), 종결(grok +1, claude는 "선택지가 하나 는 것이지 지점이 는 것이 아니다", codex 없음). claude의 −1~−3은 D2·D5·D7의 다른 안과 비교해서 줄어든 수다 `[코디네이터 판단]`.
- 되돌리기: 셈법 자체는 무관하다. 수치는 #11의 분모에 들어간다.

### D10. 순액 반환을 닫는 상태 → U6
- codex §10 “결재 상태는 모두 `완료`이고, 순액 양수는 지급 처리, 0은 차액 없음 처리, 음수는 반환 처리 대기 후 재무의 반환 사실 기록으로 닫는다.” 반환 기한 초안은 5영업일이다(PRC-16.2-1).
- grok U4 “상태 이름은 `지급 처리됨` 하나이고, 사건의 방향만 `지급` 또는 `반환`이다.”
- claude §15 `반환 대기` “정산만. 순액 < 0으로 반환 청구가 기록된 문서(§5.1)” → 반환 확인 → `지급 처리됨`. 기한은 R8의 [N]영업일이다.
- 실질 차이: 반환 완료를 기록하는 사건이 있는가(codex·claude 예, grok 아니오). 어느 축인가(codex는 집행, grok·claude는 문서). 0원을 무엇으로 닫는가(codex는 별도 `차액 없음 처리됨`, grok·claude는 `지급 처리됨`).
- 스스로 적은 약점: codex §15 “기간은 [미확인]”, grok U4 “화면만 보면 돈이 어디로 가는지 안 보인다”, claude §11 D “재무팀 지점이 음수 건마다 하나 는다.”
- 되돌리기: 중간에서 어려움 사이다. 상태 이름, S10의 닫는 사건, `TRV-11-2` 보완에 걸린다.

### D11. 규정 초안이 서로 반대로 가는 곳 → C10 (결정은 #20의 몫이다. 되돌리려면 대표이사 개정이 필요하다, ADR-0022)
- 위약금: codex TRV-11.2-1 “반려 사실만으로 출장자 부담으로 확정하지 않는다”, grok PRC-4-3 “완료 전에 생긴 예약의 위약금을 회사가 부담하는지 여부는 이 규정이 정하지 않는다.”, claude R3 “사전승인이 완료되기 전에 한 예약에서 생긴 위약금은 출장자가 부담한다.”(재심 반려 뒤에는 회사가 부담한다는 R4가 짝이다).
- 재기안 때 적용 판(`PRC-2-2`): codex PRC-2-4 “같은 출장의 반려 후 재기안은 최초 사전승인 기안일의 적용 판을 바꾸지 않는다.”, claude R6 “판을 정하는 기안일은 완료된 기안 차수의 기안일로 한다.”, grok은 언급 없음.

- **U5** — 완료된 사전승인을 다시 열지 않으므로 `PRC-9-2`(travel-procedure.md:158)·PRD:133과 규정 예외 없이 맞는다. 사전승인에 재무합의를 새로 만들지 않는다(A11). 완료 건 부분은 codex §15가 추천하지 않은 선택지 “B 정산에서만 쟁점 검토”와 가깝지만, 이 안은 플래그를 버리지 않고 그 출장의 정산 카드로 넘긴다. 약점: 정산이 없는(취소된) 출장의 완료 사전승인은 검토할 자리가 없다(§7-3, #20).

## 6. 코디네이터 결정 (10) — 사용자에게 알림, 이의 없음

- **C1** 반려 뒤 상태 이름은 `반려`를 유지한다(codex·grok). 의미는 U1·U2가 정한다. CONTEXT.md:81 "`진행중` → `반려` → 기안자에게 전달", :121·:128, ARCHITECTURE.md:324가 모두 `반려`를 상태로 쓴다. 이름만 바꾸는 것이라 되돌리기 쉽다.
- **C2** 보류 중 반려를 허용한다(codex §7, claude §16. grok 전이 표에는 없음). ARCHITECTURE.md:314 "반려·보류는 늘 받는다", ADR-0012:46. 전이 한 행이다. 보류 중 승인·동의는 U3이 정했다.
- **C3** 증빙 축은 기존 이름만 쓰고 추출 진행 중은 `job`으로 둔다(grok·claude). codex의 `추출 전/추출 중`·`추출 완료`는 표시 층으로 내린다. ADR-0011:43(업무·실행·표시 세 층), ARCHITECTURE.md:309. codex §6 표도 이것을 "진행 표시"라고 부른다.
- **C4** 입력을 바꾼 보류 답변은 ADR-0003:26 개정으로 표시한다. ADR-0003:26, CONTEXT.md:88. 세 안 모두 이 문장과 어긋난다(§4 9번).
- **C5** 상신 뒤 기안자의 직접 수정은 `결재대기`·`재무합의대기` 중에는 거절한다(grok §4.1, claude §6.1. codex는 명시 없음). ARCHITECTURE.md:240 `STALE_REVISION`, approval-matrix.md:256. 가드 하나라 나중에 풀기 쉽다.
- **C6** 거절에는 이유를 말하는 이름을 붙이고 `UNDEFINED_BY_17`은 정말 미정인 자리에만 남긴다(grok·claude 방식). ADR-0011:35-37·:96 — #17이 정하면 리듀서 표에 행을 더한다.
- **C7** 사전승인 재심의 규정 문언은 #20으로 넘긴다. travel-procedure.md:158, PRD.md:133. U5로 완료 건은 다시 열지 않으므로 완료 건 예외 문언은 필요 없다.
- **C8** 값 변경에 따른 되돌림의 행위자는 system이다 — 변경을 수락할 때 정한다(codex §2, claude §6.1. D1). 감사 이벤트의 행위자·책임자 열(ADR-0012:29-31)에 사람의 복귀 명령(grok §5)을 따로 두지 않는다.
- **C9** 항목별 부분 승인 불채택은 세 레인의 합의다(A12, codex §5.2·grok §4.2·claude §6.2). 일부 항목이 미정이어도 정상 항목부터 지급하지 않는다. ADR-0003의 provisional 표지 해제(claude ADR-0028)는 ADR 작성 때 함께 본다.
- **C10** 위약금·재기안 적용 판·보류 답변 기한 값 등 서로 반대로 가는 규정 초안 세 안(D11)은 고르지 않고 #20에 넘긴다. 규정은 대표이사 개정 사항이다(ADR-0022).
