## 1. 추천과 판단의 중심

**B1(Messages API 수동 루프) + PostgreSQL 기반 자체 상태 기계, React/Vite + TypeScript/Fastify + SSE, PostgreSQL + 비공개 R2 객체 저장소, 단일 VM의 공개 체험 링크**를 추천한다. 로컬 Compose 실행은 같은 구성의 재현 경로로 제공한다. Temporal·Inngest·LangGraph는 첫 구현에 넣지 않는다. 아래의 구현 방식·필드·운영 수치는 모두 **[설계 제안]**이며 제품이 이미 제공하는 기능이나 실측 결과라는 주장이 아니다.

이 제품의 오래 사는 것은 Claude 대화가 아니라 출장 문서와 사람의 판단 기록이다. 사람 결재를 기다릴 때는 작업을 DB에 남기고 실행을 끝낸다. 질문 답변이나 추출처럼 모델이 필요한 순간에만 짧은 실행을 새로 시작한다. 그러면 결재선, 책임자, 출처와 원본을 런타임 세션 수명에 묶지 않고 보존할 수 있다. 근거는 사람이 결재하고 에이전트는 결재 밖의 조작을 한다는 `CONTEXT.md:326-331`, `docs/PRD.md:141`, 상태와 책임의 검증 요구 `docs/PRD.md:160-163`이다.

## 2. 평가 계약 — 세 축을 분리한다

표의 R-a=진행 스트리밍, R-b=프로세스 없는 수일 결재 대기, R-c=다건·여러 승인자 큐, R-d=중단·재개, **R-e=행위자/책임자 분리(필수)**, R-f=전결·반려·순차 차단형 재무합의, R-g=필드 출처 3종이다. #4의 C1~C5는 각각 R-b/f, R-b/d, R-a, R-e/g, R-c로 확장해 읽었다(`docs/research/agent-runtime-candidates.md:19-27`).

**평가 단위는 완성된 조합이다.** UI나 SSE가 감사 모델을 제공한다고 주장하지 않는다. 아래 표에서 **공통 계약 M**은 다음을 앱 서버와 DB가 직접 구현하는 조건이다. 이 조건 없이 런타임 로그·브라우저의 `approver` 한 칸만 남기는 구성은 R-e 탈락이다. 반대로 벤더가 신원 필드를 내장하지 않았다는 이유만으로 별도 기록 가능한 런타임 전체를 탈락시키지는 않는다.

Temporal은 강한 대안이다. **90일 대기로 탈락시키지 않는다.** #4 `:937`은 Cloud 보존 기간을 승인 대기 상한으로 연결하지만, [Temporal Retention Period](https://docs.temporal.io/temporal-service/temporal-server#what-is-a-retention-period)(2026-09-22)는 **종료된 Workflow Execution**의 자료 보존으로 정의한다. [Workflow Execution](https://docs.temporal.io/workflow-execution)(2026-09-22)도 장기간 내구 실행과 복구를 설명한다. 이 재확인은 #4와 다른 판정이고 원문은 수정하지 않았다. 별도 엔진을 보류하는 이유는 결재 상태·감사 DB를 어차피 구현해야 하는 현재 MVP에서 실행 엔진의 추가 상태와 운영 면까지 늘리지 않으려는 설계 판단이다. “Temporal은 SSE를 못 한다”도 근거로 쓰지 않는다. 별도 중계로 해결 가능한 요구다.

### 3.3 자체 구현이 책임지는 구체적 복구 계약

1. **업무 상태, 실행 상태, 표시 상태를 나눈다.** 문서가 `재무합의대기`여도 `agentRun`은 종료돼 있고 worker slot은 반환된다. 승인자 큐에 보이는 문서 수와 동시에 API를 호출하는 수를 같게 세지 않는다.
2. 작업은 입력 revision·정책 판·모델 식별자·prompt 버전·schema 버전·attempt를 고정한다. API 호출 전에 작업 의도를 저장하고, 완성된 모델 응답과 도구 결과를 다음 턴 이전에 저장한다. 부분 토큰은 확정값이 아니므로 끊긴 응답은 미완료로 남긴다.
3. worker는 짧은 DB 트랜잭션으로 작업 lease를 획득하고 밖에서 API를 호출한다. 행 잠금 `SKIP LOCKED`는 큐형 소비에 사용할 수 있지만 일반 업무 조회에는 부적절하다는 [PostgreSQL SELECT 문서](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)(2026-09-22)의 제한을 따른다. API 대기 동안 DB 트랜잭션을 열어 두지 않는다.
4. lease 만료 후 재실행에는 generation/fencing 값을 사용해 이전 worker의 늦은 결과를 거절한다. 도구 실행 key는 `(runId, toolUseId)`로 중복을 막는다. 외부 응답 직후·DB 저장 직전의 장애에는 재호출 비용과 다른 모델 출력이 생길 수 있다. **API exactly-once는 주장하지 않는다.** 업무 반영은 revision·명령 key로 한 번만 받아들이고, 결과가 불명확한 쓰기는 조회·대조한 뒤 처리한다. 모의 커넥터의 그 계약은 #10이 정한다.
5. 실행 중단은 cancel 요청을 영속화하고 새 도구 실행을 막으며, 마지막 완료 checkpoint에서 재개한다. 이미 커밋한 사람의 결재를 취소하거나 되돌리는 뜻이 아니다. 사람의 보류는 별도의 도메인 상태다. worker 재시도 소진은 실패 표시이며 반려로 바꾸지 않는다.
6. 잠정 운영 범위는 **동시 LLM 작업 2개, 실행 중 문서당 1개**다[설계 가정]. 수십 개 대기 문서는 그대로 조회 가능하다. 실제 API 계정 한도·PDF 메모리 측정에 따라 조정하며 처리량 실측을 주장하지 않는다. 배포 후 code/schema가 바뀌면 버전 호환 worker 또는 명시적 migration 없이는 오래된 작업을 자동 재개하지 않는다.

**반증 조건:** API 응답 저장 직전·명령 저장 직후·lease 만료 시점에 프로세스를 끊었을 때 필드 이력 누락, 중복 결재, 무기한 고립 작업 중 하나라도 재현되면 이 구현은 채택 조건을 통과하지 못한다. 상태 기계 복잡성 때문에 이 계약을 안정적으로 구현하기 어렵다면 Temporal 도입으로 추천을 바꾼다. 이것은 향후 구현 검수 조건이며 실행 완료 주장이나 #11의 Eval 집합 확정이 아니다.

## 4. 웹 — React/Vite + Fastify + SSE

React로 다건 목록·선택 문서·수기 확정 폼을 구성하고 Vite 정적 빌드를 같은 origin에서 제공한다. API 서버와 CPU를 쓰는 PDF worker는 분리한다. TypeScript는 이미 있는 타입 경계의 이식·검토 비용을 줄이려는 선택이다. **TS로 쓰인 설계 문서가 TS 런타임을 강제하지는 않는다.** Python으로도 동등한 스키마 검증·출처 보존·입력 경계를 구현할 수 있다. `Confirmed<T>`/`PolicyFacts`의 의미를 지키는 것이 구속이고 언어 선택은 아니다(`docs/design/receipt-pipeline.md:774-798`, `:880-925`; ADR-0008 `docs/adr/0008-extraction-uncertainty-is-first-class.md:27-33`). TS의 정적 타입만 믿지 않고 API·모델·DB 입력 경계에서 런타임 검증한다.

| 웹 후보 | R-a | R-b | R-c | R-d | R-e 필수 | R-f | R-g |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **React/Vite + Fastify + SSE 채택** | SSE 업무 이벤트, POST 명령 | M 상태 조회, 연결 종료해도 대기 | 승인자·문서별 목록, 한 구독에 다중 문서 | snapshot+cursor 재접속 | 서버 M으로 충족 | 서버 allowedActions를 UI가 표시 | 필드별 출처·크롭·원본 렌더 |
| Next.js + worker + SSE 가능 | Route Handler 스트림 | M+worker로 요청 수명에서 분리 | React 목록·상세 | M snapshot+cursor | 서버 M으로 충족 | 같은 가드 필요 | 같은 필드 계약 가능 |
| React + Fastify + WebSocket 가능 | 양방향 메시지 | 연결 밖 M 필요 | 채널 다중화 직접 | ACK·cursor·재전송 직접 | 서버 M으로 충족 | 같은 가드 필요 | 같은 필드 계약 가능 |

| 브라우저가 직접 Claude 호출·상태 보유 탈락 | 토큰 전달 가능 | 브라우저 수명에 의존 | 로컬 화면 한정 | 내구 재개 없음 | **탈락: 신뢰할 서버 귀속·감사 없음** | 브라우저 조작으로 가드 우회 | 출처 이력 권위 없음 |

제품 사실: [Vite static deployment](https://vite.dev/guide/static-deploy.html), [Fastify Reply의 streams](https://fastify.dev/docs/latest/Reference/Reply/#streams), [Next.js Route Handlers](https://nextjs.org/docs/app/api-reference/file-conventions/route), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)(각 2026-09-22 확인). Fastify 스트림은 응답 검증을 자동으로 거치지 않으므로 이벤트를 직렬화하기 전에 우리 schema 검증이 필요하다. WebSocket·폴링 행은 같은 M을 붙일 때의 설계 비교다.

선택 이유는 #8이 확정한 다건 배열이 서버 렌더링의 문제가 아니라 **동시에 오래 사는 여러 업무 상태를 읽는 문제**라는 것이다. Next.js도 충족한다. 다만 별도 worker가 필요한 조건에서 웹까지 하나의 요청 실행 모델로 묶는 이득이 작다고 판단한다. SSR 성능이나 개발 생산성 우위를 실측했다고 주장하지 않는다.

**진행 상황 전달 계약:** 한 화면이 승인자 큐의 여러 문서를 한 SSE 연결로 구독한다. 확정 이벤트에는 문서 revision과 영속 cursor를 붙인다. 초기 snapshot과 cursor를 같은 일관된 읽기 경계에서 얻고 이후 이벤트를 읽는다. cursor는 단순 sequence 할당 순서가 commit 순서라는 가정을 하지 않으며, outbox 배포자가 확정한 순서로 제공한다. 중복은 eventId로 제거하고 오래된 revision은 적용하지 않는다. 이력 범위 밖 cursor는 전체 snapshot 재조회로 회복한다. SSE의 `id`/`Last-Event-ID`는 재연결 표준 수단일 뿐, 서버의 이력 보존·재생까지 제공하지 않는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html), 2026-09-22).

모델 토큰은 임시 미리보기로만 취급한다. 주요 화면에는 `추출 중 → 검산 완료 → 짝 확인 대기` 같은 확정 단계와 실패·대기 사유를 보인다. 스트림 단절은 업무 취소가 아니다. SSE 실패 시 snapshot 폴링으로 내려가되 연결 상태를 표시한다. 명령 응답이 유실되면 동일 commandId로 결과를 조회·재요청한다. 같은 origin의 서버 세션을 사용하고 이벤트·증빙 조회에도 문서 접근 권한을 검사한다.

#8의 **기한순 평평한 목록, 읽기 전용 다가오는 건, gate=on, diff=all, 승인 후 자동 이동·일괄 승인 없음, 정책 대조 별도 구획**을 그대로 수용한다([#8 확정 댓글](https://github.com/DHChe/E2EAI_business_proj/issues/8#issuecomment-5769586450), 2026-09-22). 디자인 토큰·컴포넌트 라이브러리·색상은 고르지 않으며 `docs/ui-guide.md:7-18`을 준수한다. **반증 조건:** 실제 대상 브라우저·프록시에서 SSE 재연결 후 목록과 상세의 revision이 어긋나거나 상태 변화가 유실되면 해당 스트림 구현은 부적합하다. 서버발 알림 외에 지속적 양방향 협업이 요구되면 WebSocket 선택을 다시 평가한다.

## 5. 저장 — PostgreSQL + 비공개 객체 저장

문서·결재선·현재 상태·필드 이력·감사·작업·outbox는 PostgreSQL에 둔다. 증빙 PDF/이미지·모델 입력 이미지·크롭은 비공개 Cloudflare R2에 두고 DB는 식별자·해시·변환 정보를 참조한다. R2는 S3 API 호환 기능을 문서화하지만 모든 S3 기능이 같다는 뜻은 아니다([R2 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), 2026-09-22). 이 제안은 기본 객체 입출력만 사용하고 잠금 보관·법적 불변 저장 기능은 전제하지 않는다.

| 저장 후보 | R-a | R-b | R-c | R-d | R-e 필수 | R-f | R-g |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **PostgreSQL + R2 채택** | outbox를 API가 SSE로 읽음 | 상태 행 영속 | 문서/승인자 조회·작업 행 잠금 | checkpoint·원본 참조 복원 | M 상태와 감사 같은 트랜잭션 | revision·역할·순서 제약 | 필드 revision+출처 enum+감사 FK |
| SQLite WAL + 로컬 파일 가능 | event 테이블→API SSE | 영속 파일로 충족 | 여러 읽기 가능, 쓰기 직렬화 | DB와 파일 함께 복구 | 단일 DB 트랜잭션 M으로 충족 | M으로 충족 | 같은 스키마 가능 |
| 런타임 transcript/벤더 로그만 탈락 | 실행 이벤트 표시는 가능 | 업무 대기와 보존 계약 불명확 | 승인자 큐 projection 별도 필요 | 세션 재개와 업무 복구 다름 | **탈락: 사람 책임·원자적 업무 감사 미보장** | 도구 permission을 역할 결재로 치환 불가 | 필드 revision 계약 없음 |

PostgreSQL의 큐 행 잠금 근거는 §3의 공식 SELECT 문서다. SQLite WAL은 읽기·쓰기가 병행 가능하나 writer는 한 번에 하나이고 같은 호스트를 요구한다([SQLite WAL §1·§2.2](https://www.sqlite.org/wal.html), 2026-09-22). 따라서 **SQLite가 R-c를 못 한다고 탈락시키지 않는다.** 웹 명령·작업 처리·스트림 조회를 분리 운영하고 이후 worker를 옮길 때 동일 저장 모델을 유지하는 편을 추천한 것이다. 두 후보의 성능·비용 우열은 [미확인], 부하 실측 전이다.

객체와 DB 사이의 분산 트랜잭션은 전제하지 않는다. 먼저 임시 객체를 올리고 hash·크기를 확인한 뒤 DB에서 첨부 완료를 커밋한다. 누락 객체는 추출 대상으로 잡지 않으며 고아 임시 객체는 업무 감사 대상과 구분해 정리한다. DB 백업만으로 증빙을 복구했다고 보지 않고 참조 객체와 정책 판을 함께 복구 검사한다. PDF는 worker에서 직접 래스터화하며 모델에 보낸 이미지 좌표계를 보존한다. 래스터화 엔진·회전 분류기 패키지는 성능·라이선스·설치 가능성을 아직 확인하지 않아 **[미확인]**이고, 배포 spike에서 확정할 하위 구현 선택으로 남긴다. ADR-0009의 방식 자체는 바꾸지 않는다.

**독립 재계산을 위한 저장 계약:** S2·S3·S10은 같은 함수 두 번 호출이 아니다. 평가자가 원문 판·확정 입력·조직·달력·환율 자료를 내보내 받아 별도 계산 경로로 결과를 대조할 수 있어야 한다. 제품의 공유 TS 모듈을 테스트 정답 생성기로 다시 부르는 것은 독립성이 없다. 정답·방법·집합은 #11이 정한다(`docs/PRD.md:147`, `:152-160`, `:175`). 금액은 통화와 최소단위를 함께 보존하고 소수 환율은 십진 표현으로 다룬다; JS number 기반 타입을 택하더라도 범위를 검증해야 하며 손실 없는 DB↔API 직렬화는 구현 검수 대상이다(`docs/design/receipt-pipeline.md:688-696`).

**반증 조건:** DB 복구 후 크롭에서 원본까지 추적할 수 없거나 과거 판으로 독립 재계산할 입력이 사라지면 이 저장 설계는 실패다. 복구·운영 비용이 로컬 단일 사용자라는 실제 요구에 비해 과하면 SQLite로 단순화한다. 객체 저장소 공급자 교체는 도메인 모델 변경이 되지 않도록 key·hash 참조 경계를 유지한다.

## 6. 실행·배포 — 공개 링크가 기본, 같은 코드의 로컬 재현

**[설계 제안]** 단일 Linux VM에서 Compose로 TLS 진입점, 정적 웹/API, 별도 worker, PostgreSQL을 운영하고 증빙은 비공개 R2를 쓴다. 공개 읽기·체험을 기본 입구로 하며 실제 Claude 추출은 서버가 허용한 샘플과 실행 예산 안에서만 제공한다. 로컬 실행은 같은 이미지·migration·seed를 사용하고 객체 저장 adapter를 로컬 디렉터리로 교체한다. Compose가 여러 컨테이너의 서비스·네트워크·볼륨을 정의하는 수단임은 [Docker Compose 문서](https://docs.docker.com/compose/)(2026-09-22)로 확인했다. VM 업체·인스턴스 가격·필요 RAM·가용성은 **[미확인]**이며 이 문서는 구매나 배포 실행을 승인하지 않는다.

| 실행 후보 | R-a | R-b | R-c | R-d | R-e 필수 | R-f | R-g |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **공개 VM + M 채택** | 서버 SSE, 실제 실행 단계 | DB 대기, worker 종료 | 브라우저별 demo 공간·승인자 큐 | 새로고침·worker 재시작 복구 | M + 데모 주체/역할 전환 이력 | 서버 가드 동일 | DB+원본 객체 |
| 로컬 Compose + M 가능 | localhost SSE | 프로세스 꺼도 볼륨 보존 | 여러 탭·역할 가능 | 볼륨 유지 재기동 | M 동일, 로컬 운영자가 신뢰 경계 | 같은 상태 기계 | DB+로컬 증빙 파일 |
| 정적 기록 재생만 보조 | 녹화/기록 재생, 실제 스트림 아님 | 과거 대기 표현만 | 미리 정한 목록 | 실제 업무 재개 입증 불가 | 기록의 두 주체는 표시 가능하나 **새 행위 감사 불가: 본제품 후보 탈락** | 정해진 장면만 표시 | 과거 출처 표시만 가능 |

공개 배포가 R-e를 자동 해결하는 것은 아니다. **데모 접속자**와 그가 선택한 **가상 사원 역할**을 모두 기록한다. 역할 전환은 그 접속자의 demo 공간 안에서만 허용하고 다른 방문자의 문서를 바꾸지 못하게 한다. 이것은 실기업 신원 인증의 입증이 아니며 S11은 합성 사건의 권한·귀속에 한정된다(`docs/PRD.md:147`, `:161`). 운영 권한·실인증의 깊이는 #1·#10과 확정한다.

### 6.1 심사자의 3분 경로 초안

시간은 효율 실측이 아니라 **스토리보드 예산**이다. 최종 시나리오는 #1 소관(`docs/PRD.md:178`)이며 아래는 배포 선택을 검토하기 위한 제안이다.

| 구간 | 심사자가 보는 것 | 실제성·대기 처리 |
| --- | --- | --- |
| 0:00~0:30 | 설치·API 키 없이 기한순 여러 문서, 현재 역할과 다가오는 건 | 준비된 합성 사건의 상태. 실운영이라고 표시하지 않음 |
| 0:30~1:15 | 정산 한 건의 사전승인 대조, 조항 원문, 숫자와 결재선 연결 | 계산 입력·판·근거를 열어 확인. 판정 권고 없음 |
| 1:15~2:15 | 샘플 증빙의 크롭/원본, 백지 수기 확정 또는 짝 확인, 감사 전후 값 | 준비된 이전 추출을 명확히 표시. 별도 실제 재추출을 시작하면 단계 스트림을 보되 완료를 필수 경로로 묶지 않음 |
| 2:15~3:00 | 재무합의의 차단, 역할별 허용 행위, 새로고침 후 같은 대기 | 승인·동의는 사람 클릭. 몇 영업일은 시간을 압축한 서로 다른 사례로 보여 주며 자동 승인·숨은 시계 조작 없음 |

합성 시나리오의 업무 날짜는 채택할 규정 판의 시행일과 맞춰야 한다. 현재 세 규정의 시행일은 2026-10-01이므로 현재 시각의 실사건처럼 seed하지 않는다(`docs/company/travel-policy.md:9-16`; `docs/company/approval-matrix.md:8-15`; `docs/company/travel-procedure.md:8-15`). 실제 추출은 준비된 구조화 JSON 재생으로 대체 완료 처리하지 않는다. 이미지 추출이 1급 기능이라는 `docs/PRD.md:67-75`를 따른다. 빠른 관람 경로는 기록을 읽는 체험이고, 실제 재추출은 별도의 실행 결과다. 준비한 기록과 live run을 화면·run 메타데이터에서 구분한다. 자체 렌더링 이미지의 성공만으로 C4를 입증하지 않는다는 제한도 유지한다(`docs/PRD.md:117`, `:159-163`).

### 6.2 비밀키·비용·보존의 제안

- Claude 키는 worker에만 주고 브라우저·정적 번들·감사 본문에 넣지 않는다. 공개 자유 업로드·자유 대화는 첫 데모에서 열지 않고 합성 샘플 선택으로 제한한다[설계 제안]. 실물 이미지의 공개·처리는 #1이 정한 뒤에만 가능하다(`docs/PRD.md:132`, `:178`).
- **월 지출 상한 50,000원 제안**은 가격 견적이 아니라 사용자가 판단할 예산이다. VM+객체+백업+모델 사용량 합계가 이 안에 드는지는 [미확인]. 예산 검토식은 `월 고정 인프라 + 객체/백업 사용료 + Σ(입력·출력·캐시 토큰별 사용량 × 해당 단가)`다[설계 제안]. 모델 사용량·최대 응답·재시도 예약분을 포함한 보수적 admission budget을 두고, 잔여 예산이 부족하면 새 실행만 차단한다. 상한 초과 시 과거 기록 열람은 유지하고 추출 미실행을 드러낸다. 청구 지연·취소된 호출 비용까지 즉시 정확히 알 수 있다는 주장은 하지 않는다.
- 업무 감사는 프로젝트 운영 동안 append-only로 보존하고 대기 건은 자동 만료시키지 않는 안을 추천한다. “다시 체험”은 기존 로그 삭제가 아니라 새 demo 공간 생성이다. 실험 공간의 삭제·보존 주기와 운영 종료 뒤 아카이브는 사용자 결정으로 남긴다. 실행 세션이나 transport 이력을 줄여도 업무 감사·원본을 함께 지우지 않는다(`CONTEXT.md:358`; `docs/adr/0010-human-routing-bounded-by-structure-measured-by-ratio.md:36-37`).
- 단일 VM의 중단은 공개 체험 가용성을 잃게 한다. 초기 운영은 자동 재시작·백업·복원 절차까지 제안하고 고가용성·무중단·가용성 수치는 주장하지 않는다. 계정 없이 보는 입구와 실행 예산 통제를 함께 만들 유지 부담을 감수하는 선택이다.

**반증 조건:** 준비된 큐에서도 3분 안에 원문·차이·책임 기록을 보지 못하거나, API 지연 때문에 첫 화면부터 기다려야 하거나, 측정 비용이 허용 예산을 넘으면 이 공개 체험 경로는 실패다. 관람과 실제 실행의 구분이 심사자에게 오히려 오해를 만들면 스토리보드를 바꿔야 한다.

## 8. #4 빈 셀 처리

**먼저 개수 정정:** #1은 “15개”라고 하지만 현재 #4 §6은 후보별 22행 + 전체 비용 1행, **23행**이다(`docs/research/agent-runtime-candidates.md:976-999`). 개수를 억지로 15로 맞추지 않고 전부 식별한다. **판정에 불필요**는 해결했다는 뜻이 아니라 미확인 상태 그대로 추천의 전제에서 제외한다는 뜻이다. B3의 내부 actor 필드 부재를 제품 전체의 영구적 불가능이라고 단정하지 않고 **내부 로그만으로 R-e를 통과했다는 근거가 없음**으로 취급한다.

| 20 | LangGraph 동시 thread 전략 `:996` | 불필요. 문서 revision+단일 active run으로 제어 |
| 21 | LangSmith Deployment 범위·가격·소스 `:997` | 불필요. 플랫폼 없이도 M 구현 필요; 비채택 대안의 모든 배포 SKU 조사는 추천을 바꾸지 않음. #4의 “반드시”와 달리 후보 축소 후 필요한 것만 조사하라는 이번 과제 범위를 적용 |
| 22 | LangSmith 감사·추적 `:998` | 불필요. trace가 R-e/g의 원장이 되는 설계를 택하지 않음 |
| 23 | 전체 실측 운영 비용 `:999` | **공개 배포 최종 선택에 필요·미확인.** §6의 월 상한·비용 항목까지 제안. 실제 이미지 집합·모델·방문량이 미정이므로 숫자를 채우지 않음. 최종 승인 전 청구 단가와 소규모 실측을 받아 판정 |

채택안에 필요한 것은 특정 벤더의 승인자 필드 발견보다 **M 스키마의 필수 두 주체, 상태와 감사의 원자성, 입력 출처의 비소실**이다. 따라서 미확인 셀을 허위로 채우지 않고, 공급자 내부 신원 기록을 쓰지 않는 설계로 R-e를 충족하도록 제안했다. 보존 기간은 §6의 프로젝트 운영 기간 안, 동시성은 초기 2작업이라는 **설계 가정**으로 두었으며 벤더 보증과 혼동하지 않는다.

## 9. ADR 후보 — 되돌리기 어려운 것만

번호는 부여하지 않는다. 아래 내용은 제안이고 `docs/adr/` 파일을 만들지 않는다.

| 제목 | 결정 초안 | 기각한 대안 | 반증·재개 조건 |
| --- | --- | --- | --- |
| 업무 대기는 모델 세션 밖에서 소유한다 | B1의 짧은 실행 + 앱 DB 상태 기계. 결재 의미론과 복구의 권위는 업무 DB | SDK defer/Managed session을 결재 원장으로 사용; 메모리 대기 | 자체 복구 결함 반복 또는 복잡한 실행 조정 요구가 증가하면 Temporal 추가 |
| 상태·감사·필드 계보를 같은 저장 경계로 묶는다 | PostgreSQL의 업무 전이와 append-only 감사·작업 생성 원자성, M 필수 | 벤더 trace 단독, `approver` 하나, 현재값만 저장 | 선택한 DB 경계로 누락·중복을 막지 못하거나 로컬 단일 사용자 범위로 확정되면 재검토 |
| 정책 판과 증빙 원본을 과거 계산에 고정한다 | 문서 원본 판+hash, 확정 입력 revision, 이미지 변환 계보를 보존 | 최신 정책만 참조, 파생 JSON 편집, 크롭만 저장 | 과거 계산 재현 실패 또는 원본 보관에 대한 사용자 제약 발생 |
| 공개 체험과 실제 실행의 증거를 분리한다 | 합성 기록 즉시 열람 + 제한된 live 실행, 각각 표시·감사 분리 | 로컬 설치가 유일 입구, 기록 재생을 live처럼 표시 | 예산·가용성·심사자 이해 검증 실패 시 로컬 중심으로 변경 |

React/Vite, Fastify, SSE, R2라는 개별 공급자 이름과 세부 ORM·PDF 패키지는 교체 가능한 구현 선택이라 각각 ADR로 늘리지 않는다. 다만 업무 상태 소유권·감사 원장·정책/증빙 계보·공개 무대 계약은 뒤늦게 바꾸면 데이터와 증거를 다시 만들어야 하므로 ADR 후보로 삼았다[설계 판단].

## 11. 티켓 경계

- **#10:** 에이전트가 호출할 도구 목록·권한·모의 커넥터 충실도·비결재 행위의 책임자 매핑·재무합의 설정 변경 주체를 정한다. 이 제안은 인증된 명령, 멱등 key, 필드 출처와 원본 참조를 받을 수 있는 기술 계약까지만 둔다. 범용 bash나 MCP 채택을 미리 확정하지 않는다(`docs/PRD.md:173-174`).
- **#11:** 모델 선택의 품질 검증, 이미지 출처별 정답 집합, S2·S3·S10의 독립 계산 방법, H/R 임계값·관측 주기·R3 실제 접촉·재량 경유율을 정한다. 이번 제안은 원기록을 보존할 뿐 표본 수·합격 threshold를 새로 결정하지 않는다(`docs/PRD.md:147`, `:175`; #8 넘길 것).
- **#12:** #8의 상호작용을 보여 줄 시각 시스템·색상·타이포·컴포넌트를 정한다. 이번 문서는 프레임워크와 데이터 전달 방식만 정한다(`docs/PRD.md:176`; `docs/ui-guide.md:20-23`).
- **#17:** 반려 이후·답 없는 보류·수기 수정 뒤 업무 재개·재심·부분 승인·순액 반환·기한 초과 상태를 정한다. 기술적 checkpoint 재개가 그 업무 전이의 답은 아니다. 미결 전이를 성공으로 기록하지 않는다(`docs/PRD.md:143`, `:161`, `:177`).
- **#1:** 최종 배포 비용·공개 범위·합성 데이터·개인정보·심사자 스토리보드를 승인한다. 본 문서 §6은 비교 가능한 초안이다(`docs/PRD.md:178`).

## 13. 제안의 검증 범위

저장소와 이슈를 읽고 후보의 필요 기능만 공식 문서로 확인했다. 제품 구현·비용 벤치마크·실제 이미지 추출·배포·사용자 시험은 수행하지 않았다. 따라서 이번 문서가 증명하는 것은 **요구를 만족시키도록 설계할 수 있는 경계와 비용의 책임 소재**까지다. 공개 가격·성능·PDF 엔진의 실행성은 미확인으로 남겼다. 구현 착수 전에는 원자적 감사/재개, 실제 PDF→입력 이미지→크롭 좌표, 다중 탭 명령 충돌, 끊긴 SSE의 snapshot 복구를 작은 통합 검수로 먼저 확인하고, Eval의 표본과 합격 판정은 #11에 맡긴다.
