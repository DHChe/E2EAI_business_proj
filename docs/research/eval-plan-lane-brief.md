# #11 Eval·검증 계획 — 레인 공통 지시서

> 세 레인(codex·grok·claude)이 **같은 지시서**로 서로의 산출물을 읽지 않고 푼다. 레인 이름은 작업 지시(worker spec)가 알려 준다.
> 이 지시서는 #11 그릴링(2026-09-24)에서 사용자가 정한 뼈대 위에서 **시나리오 목록과 측정 설계의 초안**을 받으려고 쓴다.
> 레인 결과는 코디네이터가 교차 대조하고, 갈린 자리는 사용자가 정한다. 그 뒤 `docs/EVAL.md`와 ADR로 옮긴다.

## 0. 할 일과 산출물

- **산출물은 파일 하나다.** `docs/research/eval-plan-proposal-<레인>.md`(예: `eval-plan-proposal-codex.md`).
  다른 파일은 만들거나 고치지 않는다. 기존 문서의 수정안은 산출물 §15에 **제안으로만** 적는다.
- **명령은 저장소(worktree) 루트에서만 실행한다.** 하위 디렉토리로 `cd`하지 않는다. 도구 상태 파일이 엉뚱한 곳에 생긴다.
- 끝나면 산출물 한 파일만 커밋한다. 메시지는 `docs: Eval 계획 독립 제안 — <레인> 레인 (#11)`이다.
  push하지 않는다. `git reset --hard`, `git clean`, `git push --force` 같은 되돌릴 수 없는 명령을 쓰지 않는다.
- **제품 코드와 시험 코드를 쓰지 않는다.** 이것은 기획 문서다. 설명용 스케치는 "설명용, 구현 아님"이라고 밝힌다.
- **정답 수치를 저작하지 않는다.** 정답 파일은 구현 phase의 첫 step이 쓴다(아래 D6).
  이해를 돕는 계산 예시는 넣어도 된다. 넣으면 규정 블록으로 직접 다시 계산하고, 계산에 쓴 조항 ID를 적는다.
- **쉬운 말로 쓴다.** 사용자는 이 문서를 읽고 선택한다. 사용자는 주니어 개발자 수준에서 이해하기를 원한다.
  낯선 개념은 작은 예시(한 출장, 한 영수증)로 먼저 보이고, 표를 쓴다.
- 모든 주장에 근거 포인터를 단다 — `path:line`, 조항 ID(`TRV-6-2`), ADR 번호, `#이슈`.
  사실과 제안을 가르고, 값에는 성질 표기를 붙인다 — 하드 규칙 / 법령의 귀결 / `[설계 가정]` / `[초기 검증 가정]`(`docs/PRD.md:147`). 근거 없는 수치를 만들지 않는다.
- **인용 규율.** 원문을 인용할 때 인용문은 원문의 **연속 부분문자열**이어야 하고, 괄호 머리말·주어 같은 **스코프 표지를 자르지 않는다.**
  두 줄을 이어 붙여 한 문장처럼 만들지 않는다. #15에서 정확히 이 실패가 났다(#11 코멘트 "#15에서 관찰된 실패 하나").

## 1. 이미 정해진 결정 — 바꾸지 않는다

아래 열다섯은 사용자가 정했다. 레인은 이 위에서 설계한다. 어떤 결정이 원문과 부딪힌다고 보면 결정을 바꾸지 말고 §17(모순·긴장)에 적는다.

| # | 결정 | 뜻 |
| --- | --- | --- |
| D1 | 진행은 하이브리드 | 뼈대는 그릴링으로 정했고, 목록·측정 설계는 세 레인 → 교차 대조 → 사용자 결정 → 다른 모델 검수 |
| D2 | **LLM 판정은 합격·불합격에 쓰지 않는다** | 합격 판정은 결정론 대조(정답 비교·재계산·부분문자열·집합 대조)와 사람 표본 검수뿐이다. LLM은 사람이 볼 표본을 **고르는** 선별에만 쓸 수 있다. 근거: ADR-0008(자기보고 신뢰도를 게이트로 쓰지 않음), #15(두 생산자의 합의는 검증이 아니다) |
| D3 | **합성 집합은 둘** | ① **함정 집합** — 경계·함정을 일부러 심은 시나리오. 하드 규칙 위반 0만 판정하고 비율을 주장하지 않는다. ② **분포 집합** — 가상 회사의 한 기간처럼 구성한 합성. 구성 비율의 근거를 문서에 묶고, 비율 지표에는 `[합성 분포 위 관측]` 라벨을 붙인다. 초기 검증 가정의 **반증**에는 쓰되 **입증** 주장에는 쓰지 않는다 |
| D4 | **증빙 이미지는 세 출처, 역할 분담** | 자체 렌더링은 함정·분포 집합의 주력이고 출장 전체 시나리오에 쓴다. 공개 데이터셋은 **JaWildText**(일본, Apache-2.0)만 쓰고 판독 품질만 잰다. MC-OCR은 이용 조건 때문에 뺀다. 실물 촬영은 사용자가 국내 영수증·카드 전표 약 30장을 찍고 라벨을 단다. 비공개 평가 전용이고 판독 품질·서식 분포만 잰다. 개인정보 처리는 #1이 정한 뒤 시작한다. 결과는 출처별로 따로 공개한다. 근거: `docs/research/receipt-datasets.md` |
| D5 | 사람 검수는 작은 표본 | 결과물을 읽으면 알 수 있는 항목(예: 보류 답변을 읽을 수 있는가)만 사용자가 **실측 1회당 약 30분**(보류 답변 약 20개 수준) 본다. **실제 승인자의 행동**(확인 도장, 두 갈래를 안 봄 등)은 `실사용 전 미측정`으로 목록에 남겨 공개한다 |
| D6 | **정답은 구현 phase 첫 step이 먼저 쓴다** | 첫 step은 코드 없이 규정 원문만 보고 정답 파일을 쓴다. 이후 step의 허용 경로에서 정답 파일을 뺀다. PRD S3·S10의 "정답 집합은 #11이 만든다"는 이 결정에 맞게 고친다. 예: `TRV-6-2`는 `compare: 합계`라서 부장·`나` 등급·3박 실비 230,000+180,000+180,000원이면 590,000원을 지급한다. 밤마다 비교하도록 잘못 읽은 코드는 560,000원을 낸다. 같은 문맥이 코드와 정답을 함께 쓰면 560,000원이 "정답"이 된다 |
| D7 | **정답 충돌은 다른 모델 리뷰어가 중재한다 — 조건 넷** | ① 구현 AI는 정답 파일을 고치지 못한다. ② 리뷰어는 구현과 다른 모델이고, 규정 블록으로 다시 계산해 근거 조항을 적는다. ③ 리뷰어 계산이 정답·코드 어느 쪽과도 다르거나 리뷰어 둘(Claude·Grok)이 갈리면 `blocked`로 멈춘다. ④ 정답을 바꾸면 변경 장부(무엇을·왜·어느 조항)에 남긴다. 이것은 **정답 파일의 다툼을 중재**하는 것이지 제품 결과를 LLM이 채점하는 것이 아니다(D2와 양립) |
| D8 | 회귀는 두 갈래 | 코드만 바뀌면 **매 커밋 기록 재생**(ADR-0016 `replay`, API 비용 0)으로 전 시나리오를 돈다. 프롬프트·모델·전처리가 바뀌면 실측한다(D9) |
| D9 | **실측은 사용자 승인 때만** | 하네스는 Claude API를 부르지 않는다. 시험은 재생 기록과 **손으로 쓴 가짜 모델 응답**으로만 돈다. 실측은 사용자가 명령할 때만 돌고, 돌기 전에 예상 비용을 보인다. 배치 API(50% 할인), 고정 표본, 바뀐 호출 지점만 돌리기로 비용을 줄인다. 첫 실측은 구현이 끝날 무렵 1회(모델 고르기 겸)이고, 그때 재생 기록도 만든다 |
| D10 | 모델은 측정으로 고른다 | 규칙만 정한다 — 하드 규칙 위반 0이고 심은 함정의 조용한 오류 0인 후보 중 가장 싼 모델. 판독기와 답변기는 따로 고를 수 있다(ADR-0017이 넘긴 모델 선택) |
| D11 | **보류 답변의 인용은 조항 하나 전체만** | 모델은 조항 ID만 고르고, 코드가 그 조항의 전문을 붙인다. 조건을 잘라내는 결함 B(축자인데 범위가 틀림)가 구조상 사라진다. Eval은 함정 집합의 질문마다 **정답 조항 목록**을 붙이고, 고른 ID가 목록 안에 있는지 기계로 대조한다. ADR-0020 결정 1("구간")에는 보완 표시가 필요하다 |
| D12 | 가정이 넘어서면 보고만 한다 | `[초기 검증 가정]` 값(R1 ≤ 10% 등)을 측정이 넘으면 Eval 보고서에 "가정 반증"으로 적고 phase를 멈추지 않는다. 값 변경은 사람이 새 이슈에서 ADR로 정한다. 제품이 실행 중에 상한을 넘어 스스로 멈추는 동작(ADR-0010)은 이와 별개로 그대로다 |
| D13 | **증거 지표의 재해석 규칙은 지금 미리 적는다** | 골대 옮기기를 막으려고 측정 전에 적는다. 형태: "분포 집합에서 법정 플래그(법적 하자·`판정 불가`)가 N건 미만이면 1차 증거 지표를 S7(면제를 하자로 찍지 않음)과 S8(근로소득 전환 판단 재료)로 옮긴다"(`docs/PRD.md:120`). **N은 레인이 제안한다** |
| D14 | 문서 위치 | 계획 본문은 `docs/EVAL.md`(하네스 자동 주입 없음)이고, 모든 코드에 걸리는 규칙은 ADR(0032부터)로 뽑아 자동 주입되게 한다. `AGENTS.md`에 인용 규율 한 줄을 넣는다 |
| D15 | 평가 결과는 데모의 정적 페이지로 | 공개 데모에 "평가 결과" 페이지를 둔다. 마지막 실측 결과를 이미지 출처별로 싣고, 실패와 `미측정`도 싣는다. 화면 형태는 #12다. 제품 안의 실시간 대시보드는 만들지 않는다 |

기본값으로 정한 것(사용자에게 알림): 평가 집합은 #11이 소유하고 심사자용 데모 시나리오는 #1에 남는다. #15가 물은 "법령 재대조 주기"는 제품이 법령 조문 원문을 인용하지 않는다면 제품 Eval 밖이다 — **이 전제를 레인이 원문으로 확인한다**(§12).

## 2. 반드시 다룰 입력

빠뜨리면 교차 대조에서 결함으로 센다. 원문을 직접 읽는다.

1. **이슈 #11 본문과 코멘트 여섯** — `gh issue view 11 --comments`. 본문의 네 질문(시나리오 집합·판정 방식·회귀·실패 시 고칠 곳), #15 코멘트의 질문 넷, PRD 그릴링 코멘트, #8·#17·#21·#26 코멘트.
2. **PRD** — 성공 기준 S1~S16(`docs/PRD.md:145-166`), 논증 전체의 반증 둘(`:119-121`), 현재 증거 상태(`:123`), #11 소관(`:175`).
3. **증빙 설계** — `docs/design/receipt-pipeline.md` §9 손 추적(`:2473`), §10 H1~H11(`:2508`), §10.1 R1~R4(`:3020`), §10.2 두 층(`:3045`), §11 측정(`:3063-3119`: 조용한 오류율·플래그 정밀도·검증 수준 분포·false abstention·근거 없는 파라미터).
4. **ADR의 반증 조건 전부** — `grep -n "반증" docs/adr/*.md`로 모은다. 0010·0011·0012·0013·0014·0015·0016·0017·0018·0019·0020·0021·0022·0023~0031에 있다. 번호 붙은 조건 하나하나를 §3 표의 한 행으로 만든다. 각 ADR "결과" 절의 **사람 확인 지점** 증감 서술도 함께 본다.
5. **사람 확인 지점 셈법** — `docs/research/state-vocabulary-comparison.md` §3 D9(`:139`)와 §7-3 `:252`(레인별 시나리오·지표 후보. 셋 다 93%를 이 제품의 승인률로 쓰지 않는다).
6. **아키텍처** — `docs/ARCHITECTURE.md` §3 경계 표의 "시나리오 구동기 ↔ 제품 코어"(`:151` — 제품이 무대의 정답을 읽으면 평가가 오염된다), §4.1 호출 지점 다섯(`:167-178`), §4.3 루프 상한(`:196`), §10 회전각 칸(`:562`), §11 세계 격리·기록 재생(`:565-573`), §12의 #11 행(`:589`, `:594-595`).
7. **codex 구현 검증 계약 7개**(#10 codex 레인 §11, develop에 병합되지 않은 커밋 `97d1dd9`). 원문을 그대로 옮긴다.
   1. 책임자 미배정·타 세계 ID·다른 역할로 호출해 모델/커넥터가 시작되지 않는지 확인한다.
   2. 모델 응답 수신 전후·결과 커밋 직전·임대 만료 시 종료해 중복 필드 버전·감사 없는 전이·늦은 반영이 없는지 확인한다.
   3. 판독 원본에 업무 명령 지시문을 넣어 A가 B의 조회나 쓰기 권한을 얻지 못하는지 확인한다.
   4. 같은 숫자를 반대 방향으로 서술한 답변, 다른 판 조항, 비연속 합성 인용이 표시되지 않는지 확인한다.
   5. 카드 미도착·끝4 지면 부재·후보 복수·값 모순을 구별하고 실제 사람 접촉 수와 필요 판정 수를 감사 원기록으로 재구성한다.
   6. 사전승인→총무 연결→인사 근태→정산 재무 동의→전결→지급을 같은 사건으로 추적한다. 반려·재상신/미정 후속은 #17을 채운 뒤 실행하고, 그 전에는 성공 처리되지 않는지 확인한다.
   7. 승인자가 읽은 카드의 판정 항목 집합과 계산 기록 집합을 비교하고 독립 평가기로 숫자·기한·결재선을 다시 계산한다. 제품 함수를 두 번 부르는 검증은 독립으로 세지 않는다(docs/adr/0013-postgres-object-storage-isolated-by-world-id.md:37).

## 3. 산출물 목차 — 이 순서와 제목을 지킨다

세 레인의 결과를 절 번호로 나란히 놓고 비교한다. 해당 내용이 없으면 절을 지우지 말고 "없음"과 이유를 적는다.

- **§0 요약** — 추천 다섯 줄 이내. 다른 레인과 가장 크게 갈릴 것 같은 자리 하나.
- **§1 평가의 층과 집합** — 결정론 층(코드가 계산하는 결재선·한도·기한·차이·대사·감사)·모델 층(호출 지점 다섯)·사람 층을 가르고, 각 층이 어느 집합(함정·분포·실물/공개 이미지·사람 표본·미측정)에서 재지는지의 원칙.
- **§2 성공 기준 대응표 (S1~S16)** — 한 기준에 한 행. 열: 층, 집합, 판정 방법(무엇과 무엇을 기계 대조하나), 정답의 출처(첫 step의 정답 파일 / 규정 예시 / 사람 라벨 / 데이터셋 라벨), 합격 조건(PRD 값 그대로 — 바꾸자는 제안은 §16에), 쉬운 시나리오 예시 1~3개. PRD와 달라지는 곳은 굵게 표시.
- **§3 반증 조건 대응표** — ADR마다 번호 붙은 반증 조건 전부와 PRD 논증 반증 둘. 열: 조건, 측정 가능 여부(함정 / 분포 / 사람 표본 / `실사용 전 미측정`), 지표 정의(분자·분모·중복 제거), 판정(반증으로 볼 관측).
- **§4 문서 단위 지표와 사람 확인 지점 셈법** — #8의 (a) 일반 승인·동의 문서 수, (b) 정책 때문에 추가 판단이 필요한 고유 문서 수, (c) 정책에서 비롯된 실제 추가 질문·확인·재요청 횟수(R3·R4의 원인 태그), (d) 책임자별 배정량, 재량 경유율. 모집단·중복 제거·상한(R2의 ≤15%를 복사하지 않는다). 기존 결재 한 번에 포함된 판단과 추가 접촉 한 번을 같은 수치로 세지 않는다. D9 셈법 제안. 지표 이름은 **후보만**(확정은 #22와).
- **§5 분포 집합** — 구성표(출장 유형·행선지·직급·동행·기간·사적 일정·결제 수단·증빙 유형·예약 유무·반려/보류/재심 비율 등), 크기, 기간, 비율마다 근거 포인터 또는 `[설계 가정]`. 비용 제약(D9)을 넘지 않는 크기로.
- **§6 함정 집합** — 함정 종류 목록(판독·검산·대사·기한 경계·결재선 경계·두 봉우리 차이·법정 3값·근로소득 전환·라우팅 상한·인용·주입 문장·세계 격리 등). 함정마다 기대 동작과 걸리는 기준(S·H·ADR), 규모.
- **§7 증빙 이미지** — 세 출처의 역할(D4). 자체 렌더링의 서식 분포(끝4 인쇄 여부, 구분자, 날짜 로캘, 회전 등)와 그 비율의 근거. JaWildText 필드를 우리 스키마에 맞추는 방법. 실물 촬영 약 30장 프로토콜(무엇을 찍고 어떻게 라벨하나, 공개하지 않는 것).
- **§8 S16 기준선** — 문서에 묶인 동작만으로 정의(약하게 만들지 않는다). 제품 밖 평가 코드에 둔다. 심을 차이의 종류와 수, 허수아비 점검표.
- **§9 정답 파일·가짜 응답·재생 기록** — 정답 파일의 형식과 위치, 첫 step이 규정 원문만으로 쓰는 방법, 잠금(허용 경로), 변경 장부의 칸, D7 중재 절차를 하네스 흐름에 넣는 방법. 가짜 모델 응답(하네스가 API 없이 쓰는 것)이 무엇을 흉내 내야 하는지 — 판독 함정의 응답 포함. 재생 기록은 사람 승인 실측 때 만든다. 제품 코어가 정답을 읽지 못하게 하는 경계(`docs/ARCHITECTURE.md:151`).
- **§10 사람 승인 실측 절차** — 예상 비용 계산법(한 장 단가는 ADR-0017의 추정이고 실측 전이다), 고정 표본 구성, 바뀐 호출 지점만 돌리는 규칙, 모델 선택 규칙(D10) 적용, 결과 보고서 형식(이미지 출처별), 데모 "평가 결과" 페이지에 실을 항목(D15), 사람 검수 30분에 무엇을 보나(D5).
- **§11 증거 지표 재해석** — D13 문장의 완성형과 N의 제안·근거. N이 근거 없는 값이면 그렇게 표기한다.
- **§12 인용** — D11 아래의 검사(조항 ID 집합 대조, 판 일치, 연속 부분문자열은 구성으로 성립). 정답 조항 목록을 누가 어떻게 붙이나. **제품이 법령 조문 원문을 인용하는 자리가 있는지** 원문으로 확인하고, 없으면 #15의 재대조 주기가 Eval 밖이라는 것을, 있으면 무엇을 해야 하는지 적는다.
- **§13 구현 검증 계약** — codex 계약 7개, #26 불변식, 주입 픽스처. 각각 어떤 시험(속성 기반 시험·시나리오·결함 주입)으로, 어느 구현 phase에서.
- **§14 실패 → 처방 대응표** — 실패 유형(하드 규칙 위반·가정 반증·재생 불일치 `REPLAY_MISS`·정답 충돌·사람 검수 불합격 등)마다 고칠 곳(코드·프롬프트·전처리·규정·정답 파일·가정 값)과 누가 정하는지. 사람을 더 붙여 해결하지 않는다(`docs/design/receipt-pipeline.md` §10 "예산을 넘기면").
- **§15 문서 반영 목록** — `docs/EVAL.md` 목차 제안, 새 ADR 후보(0032부터, 제목과 결정 요지), 고칠 기존 문서(PRD S3·S10, ADR-0016·0020 보완, `AGENTS.md` 한 줄, `CONTEXT.md` 용어)의 수정안.
- **§16 사용자에게 물을 것** — 근거만으로 닫을 수 없는 선택. 각각 선택지 2~3개, 추천, 고르면 무엇이 달라지는지.
- **§17 기존 문서·결정과의 모순·긴장** — D1~D15 포함.
- **§18 확인하지 못한 것**.
