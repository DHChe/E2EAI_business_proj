# 에이전트 아키텍처 독립 제안 — codex 레인 (#10)

작성·근거 확인: 2026-09-22. 상태: **독립 제안, 미채택**. 제품 구현·규정 개정·새 ADR 게시가 아니다. 다른 #10 레인의 산출물을 읽지 않았다. 아래에서 기존 계약을 인용한 문장을 제외한 추천, 도구 이름, 배정, 스키마 및 실패 대응은 모두 **[설계 가정]**이다. 성능·품질·시간 절감을 실측한 문서가 아니다.

## 0. 추천과 읽는 법

**에이전트는 2개다: 문서 판독 에이전트와 근거 설명 에이전트. 에이전트에게 부작용 도구는 없다.** 판독 에이전트는 원본을 구조화한 후보를 내고, 설명 에이전트는 이미 확정된 계산 기록과 조항을 읽는다. 코드가 후보 검증·계산·대사·라우팅·상태 전이·저장을 맡는다. 사람의 권한을 모방하는 인사·총무·재무 에이전트는 두지 않는다.

**비결재 조작의 책임자는 ‘그 결과를 운영상 통제하는 업무 담당자’로 작업 전에 배정한다.** 추출·금액 계산·대사는 재무 담당자, 일정·조직·결재선·기한 계산은 인사 담당자, 여행사 판독·예약 연결·카드 수집은 총무 담당자, 기안 초안과 기안은 기안자, 보류 답변의 에이전트 작성은 질문한 승인자다. 사람 자신의 수기 확정·판단·답변은 그 사람이 책임진다. 이것은 전건 확인 의무나 과실의 법적 귀속을 뜻하지 않으며, 승인 책임을 이전하지도 않는다. 세부 배정표는 §6이다.

| 다섯 물음 | 추천 하나 | 추천의 핵심 이유 | 틀리는 조건 |
| --- | --- | --- | --- |
| 몇 개인가 | 권한이 다른 에이전트 2개 | 원본의 지시문·오독이 설명용 조회 권한과 대화 이력에 직접 섞이지 않게 한다 | 두 작업이 항상 동일 입력·동일 권한이어도 같은 격리·품질을 더 단순하게 보장함 |
| 무엇을 책임지는가 | LLM은 판독 후보·서술, 코드는 모든 수치·규칙 판정 | 숫자와 판정의 독립 재계산이 가능해야 한다 | 서술이 새 판정 입력을 만들거나 별도 재계산에서 값이 달라짐 |
| 어떤 도구인가 | 설명용 읽기 3개, 판독용 동적 도구 0개, 커넥터는 코드 소유 | 모델은 업무 변경 명령을 선택할 수 없다 | 단일 작업에 사람이 확인할 외부 부작용·보상 연쇄가 꼭 필요함 |
| 어디서 사람인가 | 기안·결재·재량·잔여 수기/짝 확인·업무 인계, 대기는 DB | 사람의 결재와 모델 작업의 수명을 분리 | 워커를 종료하면 대기나 답변 대상자가 사라짐 |
| 상태·감사는 | 단일 명령 처리기 + 원자적 감사 + 업무 담당자 배정 | 책임 없는 실행과 일부만 저장되는 전이를 차단 | 미배정 실행·감사 없는 반영·세계 간 참조가 하나라도 재현됨 |

근거 축은 [Issue #10 본문·갱신 1~3](https://github.com/DHChe/E2EAI_business_proj/issues/10)(확인 2026-09-22), `CONTEXT.md:326-345`, `docs/PRD.md:151-165`다. #9의 결정은 전제로 채택한다: `docs/adr/0011-messages-api-direct-waits-are-document-state.md:25-47`, `docs/adr/0012-transition-audit-provenance-in-one-transaction.md:23-46`, `docs/adr/0013-postgres-object-storage-isolated-by-world-id.md:25-38`, `docs/adr/0014-apv-9-3-exposed-declaratively.md:27-33`, `docs/adr/0015-typescript-web-stage-sse-no-unverified-answer-text.md:23-29`, `docs/adr/0016-record-and-replay-model-calls.md:24-35`, `docs/adr/0017-public-demo-single-vm-replay-default-capped-live.md:23-46`.

소스 탐색은 `graft map`과 `graft ask ... --source`로 시작했으나 인덱스가 0개이고 결과가 없었다. 과제의 빈 인덱스 예외에 따라 파일 목록·문서 제목 검색과 필요한 범위 읽기로 전환했다. 외부 제품·API·가격에 대한 새 사실 주장은 추가하지 않는다. 기존 조사에 의존하는 사실은 해당 저장소 줄에 귀속한다.

## 1. 에이전트 수와 경계

### 1.1 무엇을 하나로 세는가

여기서 에이전트 하나는 **독립된 모델 작업 계약·입력 허용 범위·출력 스키마·도구 허용 목록** 하나다. 프로세스 수나 모델 이름 수가 아니다. 두 에이전트는 같은 worker 서비스와 모델 호출 adapter를 써도 된다. 대화 이력과 권한은 공유하지 않는다. 좁은 의미로 도구 선택 루프만 에이전트라 부르면 ‘근거 설명 에이전트 1개 + 판독 모델 작업 1종’이다. 이 제안의 **2개**는 판독도 에이전트 작업으로 세는 명시적 관례이며, 숨은 supervisor는 없다.

문서 판독의 분류 호출과 유형별 추출 호출을 별도 에이전트로 세지 않는다. 둘 사이의 경로 선택은 코드가 하고 읽기 권한은 같은 원본 범위다(`docs/design/receipt-pipeline.md:62-74`). 여행사 이메일 판독도 같은 신뢰 경계의 별도 스키마다. 방향 분류 모델은 정해진 입력에서 각도만 내는 전처리 부품으로, 도구를 고르는 업무 에이전트가 아니다.

### 1.2 구성도

아래는 설명용 구성도이며 구현이 아니다. 화살표는 데이터·명령 전달이고 에이전트 간 직접 위임 경로는 없다.

```text
기안자 / 승인자 / 인사 / 총무 / 재무 / 내부감사
                  │ 인증된 명령          ▲ 큐·원문·확정 답변·감사
                  ▼                      │
        [API + 권한 검사 + 단일 명령 처리기] ── [카드 투영 + SSE/outbox]
                  │ 한 DB 트랜잭션             ▲
                  ▼                           │
 [PostgreSQL: world_id / 문서 revision / 필드 이력 / 감사 / job / model_call]
          │ job 임대                   ▲ 후보·검증 결과 수락
          ▼                            │
 [worker: 실행 계획·책임 배정 확인·검증·계산·대사·라우팅]
    ├─ [A 문서 판독] ← 배정 원본만 ← [전처리] ← [비공개 객체 저장소]
    ├─ [B 근거 설명] → 읽기 3도구 → [고정 revision 계산 기록·조항]
    ├─ [TRV/PRC/APV 로더 + 규칙 계산 + 법정 판정 코드]
    └─ [모의 커넥터 adapter] ↔ [한성워크 / ERP / 여행사 이메일 / 카드 CSV]
                                            (세계별 합성 자료)
```

객체와 DB의 원자성을 주장하지 않는다. 임시 객체 업로드·해시 검증 뒤 DB에 첨부를 확정하고, 누락 객체로 추출을 시작하지 않는다(`docs/adr/0013-postgres-object-storage-isolated-by-world-id.md:27-30`). 사람 대기에는 worker가 없다(`docs/adr/0011-messages-api-direct-waits-are-document-state.md:31-32`).

내부 함수마다 서비스·에이전트를 만들지 않는다. 검산·대사·법정 판정·정책 계산은 독립 입력/출력 계약을 가진 코드 모듈이고, 같은 worker 안에서 실행한다. 각 단계 결과를 남겨 실패한 단계부터 새 job으로 재실행할 수 있게 하는 정도가 필요한 분리다.

### 1.4 분할 후보 비교

모든 후보는 결재를 사람에게 둔다는 같은 조건으로 비교한다. ‘1개’가 본질적으로 불안전하거나 ‘많을수록 정확하다’고 주장하지 않는다. 각 셀은 구현해야 할 장치와 분할에 따른 부담에 대한 **[설계 가정]**이다.

| 비교 축·구속 | 더 적게: 단일 에이전트 + 코드 | 추천: 판독 A + 설명 B + 코드 | 더 많이: 판독·정책 설명·인사·총무·재무·조정 6개 + 코드 |
| --- | --- | --- | --- |
| 실패 격리 | 모드별 이력 초기화를 빠뜨리면 오독·지시문이 설명으로 전파 | 입력 신뢰 수준별 계약으로 전파 경로 절단 | 인계 메시지마다 검증·중복 방지가 늘고 설명 책임 분산 |
| 권한 | 요청마다 allowlist를 바꿔야 함; 완전히 분리하면 사실상 추천안의 두 계약 | A 동적 도구 없음, B 고정 조회 3개 | 팀별 권한의 상당 부분은 사람이 가진 권한이므로 모델에 줄 도구가 없음 |
| 책임 | 한 agent_id로 작업 종류를 별도 추적 | 작업 계약 + 업무 책임자 + 모델 호출 연결 | 조정자가 실패를 팀 에이전트에 돌려도 사람 책임은 별도 필요 |
| 결재 행위자 사람 (`CONTEXT.md:331`) | 공통 명령 가드 필요 | 사람 세션만 결재 입력 | 6개 모두 같은 가드, 팀 명칭이 결재 대행처럼 보일 위험 |
| S5 재량 자동 확정 금지 (`docs/PRD.md:155`) | 출력 모드 구분·코드 관문 | A 후보, B 판단 불가 반환, 코드 관문 | 모든 에이전트 사이 메시지에도 관문 필요 |
| S4 원문 인용 (`docs/PRD.md:154`) | 코드가 조항 렌더 | B는 조항 ref만 선택, 원문은 코드가 렌더 | 중간 요약을 인용으로 승격시키지 않는 추가 통제 |
| S2·S3·S10 독립 재계산 (`docs/PRD.md:152-153`, `:160`) | 코드만 계산하면 충족 가능 | 동일 코드 기록, 독립 평가기 입력 보존 | 정책 에이전트를 늘려도 계산 권한은 코드에 남음 |
| S15 카드 완전성 (`docs/PRD.md:165`) | 서술 대신 공통 판정 기록으로 투영 | B 실패해도 판정 기록 전체를 카드에 표시 | 팀별 요약을 합칠 때 누락 방지 집합 대조 필요 |
| S12 H1~H11 (`docs/PRD.md:162`) | 단일 코드 라우터 | 같은 라우터, B는 새 확인 작업 생성 불가 | 팀 에이전트별 질문 발행 금지·전역 중복 억제 필요 |
| 검증 전 문장 비노출 (docs/adr/0015-typescript-web-stage-sse-no-unverified-answer-text.md:26) | 공통 검증 완료 경계 | B 전용 출구, A 출력은 내부 후보 | 모든 자연어 출구에 같은 검증 필요 |
| 모델 기록·재생 (docs/adr/0016-record-and-replay-model-calls.md:24-35) | 하나의 모드 식별 추가 | 두 계약별 프롬프트·스키마 해시 | 호출 경로·메시지 의존 수가 늘어 재생 기록 관리 증가 |
| world_id 격리 (docs/adr/0013-postgres-object-storage-isolated-by-world-id.md:31-32) | 세션·조회 가드 | 두 계약에 동일 서버 envelope | 모든 인계에서 세계 키 전파·검사 |
| 전이·감사·출처 한 트랜잭션 (docs/adr/0012-transition-audit-provenance-in-one-transaction.md:23-43) | 단일 명령 처리기 | 단일 명령 처리기 | 독립 팀 쓰기는 금지해야 충족 가능 |
| 채택 판단 | 안전하게 구현 가능하나 작업 모드 격리를 매번 확인하는 부담 | 권한 경계 1개로 유의미한 위험 둘을 구별 | 팀 경계는 사람·명령 권한으로 충분; 추가 에이전트의 실패 격리 이득 미입증 |

**추천이 틀리는 조건:** A와 B의 프롬프트·권한·자료 범위가 실제로 동일해져 계약을 나눌 이유가 없으면 1개로 합친다. 반대로 여행사 업무가 예약·취소·보상 실행으로 확대되고 독립 권한·복구 단위를 요구하면 그 작업만 분리한다. 현재 예약 검색·발권·변경 처리는 제외다(`docs/PRD.md:133`).

## 2. 책임 — 숫자는 결정론적 코드, 서술만 LLM

### 2.1 구성 요소별 하는 일과 하지 않는 일

| 구성 요소 | 한다 | 하지 않는다 |
| --- | --- | --- |

### 2.2 ADR-7 패턴은 ‘계산 권한’으로 채택하고 출력 검증을 더한다

Issue #10 갱신 2의 **‘숫자는 SQL, 서술만 Claude’ 패턴을 수정 채택**한다. SQL 집계와 TypeScript 순수 계산 중 어느 언어로 계산하느냐보다 LLM이 계산의 원본이 되지 않는 것이 계약이다. 코드가 금액·통화·단위·적용 조항·입력 revision·표시 문자열을 가진 `calculation_record`를 만든다. B는 이 기록의 항목 ID와 조항 ID를 선택하고, 서버가 숫자·인용을 끼워 넣는다.

설명용 출력 스케치이며 구현이 아니다:

```text
answer = [서술 조각, {calculation_ref}, {clause_ref, span_start, span_end}, ...]
문서/계산 revision 일치 → 숫자·단위와 인용 범위 검사 → 완성 답변 저장 → 표시
```

프롬프트에 ‘그대로 인용’이라고 써 놓는 것만으로 환각이 구조적으로 불가능해지지는 않는다는 것이 이 제안의 판단이다. 계산이 120,000원 초과라도 LLM이 ‘한도 이내’라고 쓰면 숫자 일치 검사만 통과할 수 있다. 따라서 금액·기한·결재선·판정 방향을 주장하는 문장은 계산 기록의 의미 태그에 대응하는 **서버 템플릿**으로 제한한다. 재량 질문은 해당 `facts_to_ask`와 판단 주체만 반환한다. 자유 서술의 의미 검증은 완전하다고 주장하지 않으며 #11 평가 대상이다. 검사 실패 시 원기록·조항만 표시하고 실패 이유를 남긴다. 답변 생성 실패 때문에 새 사람 확인을 자동 발행하지 않는다.

직접 확인한 SlipScan은 `/Users/astralpig/DEV/fc-Agentic-Workflow-prac/lib/claude/report.ts:80-98`에서 `aggregateMonth`와 `formatRatio`를 써 프롬프트 입력을 만든다. ‘SQL’은 역할 분리 패턴의 이름으로 읽으며 이 구간 자체를 SQL 실행이라고 인용하지 않는다. `/Users/astralpig/DEV/fc-Agentic-Workflow-prac/lib/pipeline/process-document.ts:294-308`의 현재 상태 조건·행 잠금 패턴은 채택하지만, 해당 저장소의 상태 이름과 타임아웃 정책은 이식하지 않는다. 원본과 Issue 요약의 불일치는 §10에 적었다.

**추천이 틀리는 조건:** 독립 재계산 입력이 빠지거나 숫자가 같은데 설명의 방향이 틀린 답이 노출되면 출력 계약이 실패다. B의 자유 서술을 더 줄여 근거 선택과 템플릿 구성만 남긴다. ‘두 번째 검토 LLM’을 정확성 보증으로 더하지 않는다.

## 3. 도구와 권한

### 3.1 부작용 도구에 대한 명시적 답

**에이전트에게 부작용 도구가 있는가: 아니오.** A는 동적 도구가 없고, B에는 아래 조회 3개만 등록한다. 모델 응답의 후보를 저장하는 부작용은 존재하지만, 사전에 배정된 job의 고정된 결과 수락 계약으로 코드가 수행한다. 모델이 `save_draft`, `sync`, `approve`, `ask_human` 같은 쓰기 도구를 선택하지 못한다. 저장된 후보·초안·답변의 내용 생성 행위자는 여전히 에이전트로 기록한다. DB writer가 코드라는 이유로 모두 시스템 행위로 바꾸지 않는다.

따라서 ADR-0011 반증 1의 **‘사람 확인이 필요한 부작용 도구 + 한 작업 안 확인 지점 둘 이상 + 그 사이 보상 필요’**를 이번 추천은 열지 않는다(`docs/adr/0011-messages-api-direct-waits-are-document-state.md:88-95`). 읽기 도구가 모델 비용·실행 기록을 발생시키는 것은 숨기지 않지만, 업무 쓰기 권한과 구별한다. 훗날 모델이 예약 요청·취소 등 실행을 선택하게 되면 ‘아니오’를 바꾸고 세 조건을 다시 평가해야 한다. 부작용 도구 하나만 추가했다고 반증 1 전체가 자동 성립한다고 쓰지 않는다.

B의 수동 루프는 job에 messages와 완료 응답을 저장한다. [설계 가정] 시작 상한은 모델 요청 3회·도구 호출 총 6회이며 초과하면 원기록만 제공하고 실패를 남긴다. 성능 수치가 아니며 #11에서 답변 품질·지연·예산으로 반증한다. 반복 도구 호출은 같은 snapshot을 반환하고, 최신 revision 변경은 현재 답변을 폐기시키는 조건이다.

**추천이 틀리는 조건:** 위 allowlist 안에서 답할 수 없는 질문이 핵심 시나리오의 대부분이면 조회 범위를 사례별로 재검토한다. 이를 이유로 범용 DB·브라우저 도구를 즉시 열지는 않는다. 수동 루프가 같은 기록을 반복 읽기만 한다면 루프를 제거하고 일회성 자료 주입으로 단순화한다.

## 4. 모의 커넥터 — 네 계통을 정직하게 흉내 낸다

### 4.1 목록과 충실도

ERP의 환율 표와 한성워크의 버전 있는 회사 달력은 **네 계통 외의 실 API를 늘리지 않는 합성 참조 자료**다. 실제 시스템에 그런 API가 있다는 주장이 아니다. 환율 누락을 카드 청구환율로 메우지 않는다. `TRV-14-1/2`의 지출일·직전 고시일 규칙에 필요한 자료를 공급한다(`docs/company/travel-policy.md:313-326`). 달력은 규정 외부라는 계약을 유지한다(`docs/company/travel-procedure.md:50-62`). 시드의 정답 라벨은 adapter가 읽는 원자료와 분리해 #11만 소유한다.

모든 import는 `world_id, source_system, source_record_id, source_revision, received_at, effective_at, payload_hash, batch_id`를 갖는다. 같은 키·같은 hash는 무효과, 같은 키·다른 hash는 명시된 정정 revision 없이는 충돌이다. 구조화 batch는 파일 전체 스키마 검사 후 원자료 snapshot으로 원자 반영하고, 결손 행이 있는 batch는 staging 상태로 남긴다. 격리 행을 0건으로 취급하거나 정상 명세의 완전성을 주장하지 않는다. 여행사 변경 통지를 받았다고 이미 연결된 예약을 자동 교체하지 않는다. 총무의 새 연결 기록으로 전후 차이를 남기되 판단은 정산에서 한다(`docs/company/travel-procedure.md:148-158`).

지연은 실시간 sleep이 아니라 주입 시계와 `available_at`로 제어한다. 데이터가 아직 오지 않은 `pending`과 도착했으나 잘못된 `invalid`, 정상적으로 없는 `absent`를 구별한다. 카드 명세 미도착을 `짝 없음`으로 처리하지 않는다(`docs/design/receipt-pipeline.md:68`). 모의 실패 분포·건수·정답은 #11/#1이 정하며, 이 제안은 만들 수 있어야 할 실패 종류만 정한다.

### 4.2 §7.5 요구 칸 단위 대조

정상 시나리오의 명세는 아래 칸을 모두 가진다. nullable이 허용된 항목은 명시적 null을 주고, 비정상 fixture의 결손을 정답으로 복구하지 않는다.

| §7.5 요구 칸 | adapter 칸·형식 | null/잘못된 값 처리와 쓰임 | 충족 근거 |
| --- | --- | --- | --- |
| 이용일(청구일 아님) | `usedAt`: 원거래의 현지 달력 날짜; `billedAt` 별도 | 없으면 행 격리·명세 오류, 청구일 대체 금지; 날짜 창 입력 | `docs/design/receipt-pipeline.md:2220`, `:1802-1803` |
| 이용금액 | `original.minor`: 정수 금액 문자열 | 분할액·환산액 대체 금지, 파싱 오류 격리 | `:2221`, `:1804-1805` |
| 원거래 통화 | `original.currency`: 명시 코드 | 누락·미지원은 운영 실패; KRW·exponent 2 가정 금지 | `:2221`, `:771-772` |
| 승인번호 | `approvalNumber`: 문자열 또는 null | 선행 0 보존, 없으면 다음 키; 번호만으로 자동 확정 금지 | `:2222`, `:1801`, `CONTEXT.md:310` |

위 표의 `:줄`은 같은 표의 `docs/design/receipt-pipeline.md`를 뜻한다. **§7.5에는 없지만 실행에 필요한 칸**도 준다: `id`, `cardLast4`, `billedKrw`, `merchantName`(`docs/design/receipt-pipeline.md:1798-1810`). 카드 끝4를 명세가 제공해도 지면에 없는 끝4를 영수증 필드에 복제하지 않는다. 경쟁 후보·추출 문제·값 모순과 끝4·금액·날짜 실제 대조 조건은 그대로다(`CONTEXT.md:310`).

가맹점 업종과 공급 분류를 같은 것으로 확정하지 않는다. adapter는 원 업종 코드·명칭·맵핑 판을 보존하고 알려진 결정론 맵핑만 코드가 적용한다. 미지원 분류는 모름으로 남긴다(`docs/design/receipt-pipeline.md:2241-2242`). 취소·정정은 원 승인 ref와 signed 금액을 보존하되, 대사 알고리즘이 지원하지 않는 경우 `UNSUPPORTED_CARD_ADJUSTMENT`로 격리한다. 환불을 보통 영수증으로 강제로 짝짓지 않으며 전체 취소 후속은 #17/구현 범위 검토로 넘긴다.

### 4.3 일정·출처 충실도

일정은 `tripId`, 날짜별 현지 날짜·장소·업무 수행 내용·업무/비업무 구분의 근거, 업무 장소 목록, 사적 일정, 동행, 숙박 기간·항공 구간과 한국 기준 출발/복귀 날짜를 구별해 보존한다. 현지 지출일을 KST로 일괄 이동시키지 않는다. 규정의 출장 일수·기한은 한국 날짜를 쓴다(`docs/design/receipt-pipeline.md:958-984`, `docs/company/travel-policy.md:50-55`, `docs/company/travel-procedure.md:66-80`). 시각대 없는 이메일을 임의로 KST 시각으로 만들어 확정하지 않는다.

구조화 카드·그룹웨어 필드는 `시스템 연동`, 여행사 이메일에서 A가 읽은 값은 `에이전트 추출`, 총무가 원문을 보고 수기로 확정한 변경값은 `사람 수기 확정`이다(`CONTEXT.md:335-345`). 단순히 연결 버튼을 눌렀다고 A의 모든 필드가 사람 수기 확정으로 바뀌지 않는다. 우리 앱이 내보냈다 다시 가져온 동일 필드도 독립된 시스템 확인으로 세지 않고 원 출처 계보를 유지한다. 시스템 연동의 우선은 **같은 사실이고 짝이 성립한 경우**에 적용한다. 예약 예정일은 실제 지출일·업무일을 자동 덮지 않는다.

**추천이 틀리는 조건:** 카드 정상 fixture에서도 요구 필드가 없거나, 이메일 대신 숨은 구조화 정답을 읽어야 S1/S12가 성립하면 충실도가 실패다. 자체 생성 자료에서의 높은 자동 대사율을 운영 가능성의 입증으로 쓰지 않는다(`docs/PRD.md:117`, `:147`, `:162`).

## 5. 사람 승인 지점과 상태 기계

### 5.1 세 상태 층

업무 상태(문서·출장·대사), 실행 상태(job 임대·재시도·실패), 표시 상태(작성 중·검사 중)는 별개다(`docs/adr/0011-messages-api-direct-waits-are-document-state.md:43-47`). 다음 상태 이름은 기존 용어를 쓰며, 대기 사유는 문서 enum을 무한히 늘리는 대신 연결된 작업 행으로 설명한다. `승인 카드 도달 전`의 정식 용어·enum 승격은 #22 소관이다.

설명용 상태 스케치이며 구현이 아니다:

```text
사전승인: 기안 준비 --사람 상신--> 결재대기[i] --사람 승인--> 다음 i / 완료
                                      ├─ 보류[같은 i, 질문 대상·ID]
                                      └─ 반려 결정 ── [#17 후속 상태 자리]
완료 --총무 예약 연결 / 인사 근태 반영--> 출장 수행 --복귀--> 정산 준비
정산: 확정 입력 --사람 상신--> 재무합의대기[j] --사람 동의--> 다음 j
                                                       └─ 마지막 j → 결재대기[i]
결재대기[i] --사람 승인--> 다음 i / 정산 완료 --재무 지급 처리--> 출장 완료
보류 --대상자의 답변 도착--> 같은 역할·같은 사람의 대기 (세부 적용은 #17)
[#17 후속 상태 자리] --#17이 정한 수정·재상신 계약--> 새 revision의 상신 입구
```

‘3자’는 인사·총무·재무의 업무 인계 구조이지 승인자 수가 항상 세 명이라는 뜻이 아니다. 사전승인에 재무합의는 없고, 정산에서는 재무 담당자와 총액 조건을 충족한 재무팀장이 순서대로 동의한 뒤 기안자의 조직 계통 결재가 시작된다. 재무합의자 본인이 기안자이면 APV-9-4의 대체 규칙을 적용한다(`docs/company/approval-matrix.md:69-71`, `:205-235`). 인사·총무를 새 결재자로 넣지 않는다(`:317`).

**권한 허용과 전이 정의 유무는 두 검사다.** 재량 미기록을 이유로 반려·보류 권한을 끄지 않는다. 그러나 #17이 목표 상태/후속 원자적 효과를 아직 정하지 않은 명령은 `UNDEFINED_BY_17`로 거절하고 **성공한 반려·보류 전이로 기록하지 않는다**. 실패한 시도는 명령 거절 기록으로 남기고 기존 업무 상태는 유지한다. #17이 정의를 채우면 동일 권한 검사 뒤 전이가 실행된다. 이는 현재 완성 제품에서 반려가 동작한다고 주장하는 설계가 아니다. `reject_always_allowed`는 최종 구현의 요구이고 현재 #17 미결 때문에 실행 불가능한 부분이 있음을 카드와 상태에 드러내야 한다. docs/adr/0011-messages-api-direct-waits-are-document-state.md:35-37과 docs/adr/0012-transition-audit-provenance-in-one-transaction.md:46 사이의 이 긴장을 숨기지 않는다(§10).

docs/adr/0003-approver-actions-three.md:25-26과 `CONTEXT.md:88`의 ‘답변 도착 후 같은 승인자 대기’는 골격으로 유지한다. 답변 없이 시간 경과, 수정값 반영, 승인 효력, 반복 보류 처리 등은 #17에서 정한다. 상신 뒤 새 짝 보류나 재량 판단으로 결재선 입력이 바뀌는 건은 기존 승인을 계속 실행하지 않고 미정 경로를 표시한다. 어느 새 상태로 돌아가는지는 #17/#21의 답을 기다린다.

### 5.3 사람에게 묻는 범위와 기다림

기안자는 자기 초안을 읽고 상신한다. A의 기안 초안은 기안자가 직접 제공한 서술·첨부를 폼 후보로 구조화하는 별도 작업이며, 정책 판단·초과 사유의 인정·누락 사실 창작은 금지한다. 증빙 추출 결과를 받은 코드가 폼에 배치하는 것과 이 초안 작성 작업은 job 종류로 구별한다. 에이전트 초안은 초안 artifact이고 자동으로 판정 입력을 만들지 않는다. 수기 확정은 배정 필드의 백지 입력(모호한 후보가 여럿이면 후보 선택), 원본 토글·사유·원본 열람 여부를 남긴다. 짝 확인은 추출 문제를 먼저 닫고, 경쟁·대조 불가면 기안자, 값 모순이면 재무합의자 순서다(`docs/design/receipt-pipeline.md:2372-2417`, `:2490-2502`). 사람 입력 뒤 재검산·재대사 실행의 필요성은 계약이고, 수정 후 어떤 문서 상태로 재개하는지는 #17이다.

H1~H11은 코드 라우터가 전역 적용한다: 수기 세션 1회, 판정 입력만 질문, 같은 사실을 시스템 연동이 확인한 필드·검산 불가 단독·해소된 모호성은 송부 0, 합계 판독 불가+짝 미성립은 재촬영, H7/H8의 좁은 성립 조건, H9 예산·H10 표본 감사 강등, H11 두 신호만 유지한다(`docs/design/receipt-pipeline.md:2306-2334`). 재량과 정책 대조는 H11의 제3 신호로 세지 않는다(`CONTEXT.md:377-380`). R1~R4의 기존 정의·초기 문턱을 바꾸지 않고 필요 판정·실제 접촉·대기·책임자 배정을 따로 저장한다(`docs/design/receipt-pipeline.md:2510-2518`).

책임자 배정은 확인 요청이 아니다. 이 제안을 채택했다고 추출 건마다 재무 담당자 확인 버튼이 생기지 않는다. 상한 초과는 미완료·대기·자동 진행 가능 수를 공개하고 해당 처리 경로를 멈추며 정상 승격하지 않는다(`docs/adr/0010-human-routing-bounded-by-structure-measured-by-ratio.md:26-39`).

**추천이 틀리는 조건:** 반려가 재량 관문 때문에 거부되거나, 재무 동의 이전에 첫 결재권자가 승인하거나, 재시작 뒤 보류의 질문·대상자가 사라지면 실패다. R 상한을 맞추려고 대기나 짝 확인을 분모/분자에서 빼야 하는 경우도 이 설계를 통과한 것으로 보지 않는다.

## 6. 상태와 감사 — 작업 전에 사람 책임자를 묶는다

### 6.1 책임자 규칙과 배정 권한

**추천: 업무 종류별 운영 책임자 + 사람이 한 입력은 그 사람.** ‘어떤 문제를 처리할 담당자인가’와 ‘그 값이 맞다고 사람이 이미 확인했는가’를 분리한다. 자동 추출을 운영하는 재무 담당자를 책임자로 적는 것은 그 사람이 매 장을 읽었다는 뜻이 아니다. 이를 감사 조회에 구별해 표시한다. 기안자는 자신이 제공한 사실·채택한 초안·상신에 책임지고 아직 보지도 않은 모델 오독 전체의 책임자는 되지 않는다.

[설계 가정] 세계를 만들 때 인사·총무·재무 팀장이 해당 업무의 기본 담당자를 실명 ID로 배정한다. 예시 인물은 인사 오하린, 총무 진서후, 재무 남윤호이며 팀장 정보는 기존 조직 설정에 있다(`docs/company/org.md:54-60`). 표의 역할은 실행 전에 그 세계의 실제 사람 ID 하나로 해소한다. 역할명 문자열·공용 계정·AI ID로 NOT NULL을 채우지 않는다. 담당자 자신이 배정 대상 사건의 기안자라 이해충돌이 생기는 **사람 판단**은 기존 APV 규칙을 따르며, 운영 배정이 결재선 대체 규칙을 만들지 않는다.

팀장은 담당 범위·유효기간·배정 사유를 기록해 비결재 운영 배정만 바꿀 수 있다. 부재자를 자동으로 팀장/기안자/admin으로 대체하지 않는다. 재배정은 새 assignment 버전이고, 기존 감사 책임자는 과거 ID를 유지한다. running job의 배정이 취소되면 결과 수락도 막고 새 배정으로 새 job을 만든다. 결재자 교체는 이 배정 기능의 범위 밖이다.

### 6.3 실행 전 차단과 원자성

설명용 계약이며 구현이 아니다:

```text
command_envelope = world + actor_from_session + operation + input_revision
                   + assignment_id/version + responsible_person_id + command_id
job = envelope + input_hash + policy_edition + model/prompt/schema_versions
      + lease + attempt + fence
허용 순서: 세계/권한 → 사람 책임 배정 → 입력/정책 판 → 전이 정의 → 작업 생성
결과 수락: assignment 유효 + fence 일치 + 기대 revision 일치 + 결과 검증
한 트랜잭션: 문서/필드 새 버전 + 감사 + 계산 계보 + 후속 job + outbox
```

배정이 없으면 `RESPONSIBLE_UNASSIGNED`로 **API 호출·파일 판독·커넥터 가져오기 전에** 막는다. rejected request의 운영 로그에는 인증된 요청자·거절 사유를 남기되 미배정 업무가 수행된 감사 이벤트를 꾸며 만들지 않는다. 배정·입력 변경과 늦은 응답 경합은 수락 시 다시 검사한다. 모델 호출은 DB 트랜잭션 밖에서 하므로 API exactly-once는 주장하지 않고, 업무 반영은 명령 key와 revision으로 한 번만 수락한다(docs/adr/0011-messages-api-direct-waits-are-document-state.md:44-47).

문서·필드·감사·작업·계산·커넥터 staging에 `world_id`를 두고 참조도 `(world_id, id)`로 묶는다. 객체 접근도 세계 권한 확인 뒤 발급하며 raw object key를 모델의 자유 입력으로 받지 않는다. 모델 재생 기록을 세계 간 공유할 때에도 원본 데이터 읽기 권한을 우회하지 않는다. [설계 가정] 시드 fixture는 허용된 합성 자산만 세계에 연결하고 실행·감사 기록은 각 세계 안에 새로 만든다.

### 6.4 필드 출처 3종과 감사 조회

`에이전트 추출 / 사람 수기 확정 / 시스템 연동`만 사용한다. 필드 새 버전마다 원값·새값·source·원본/연동 record·검증 수준·실제 행위자·책임자·관련 명령/job/model_call을 함께 참조한다. 계산값은 네 번째 source가 아니라 계산 기록의 결과이며 원 입력의 필드 버전 목록으로 이어진다(docs/adr/0012-transition-audit-provenance-in-one-transaction.md:41-43). 초안의 미확정 후보와 답변의 자유 서술은 artifact이지 판정 입력 필드가 아니다. 사람이 채택해 입력으로 만들 때만 별도 확인 명령과 필드 provenance를 만든다.

수기 확정은 기존 에이전트 값을 지우지 않고 사유·`originalViewed`·크롭과 원본 hash·새값을 남긴다(docs/adr/0009-evidence-is-crop-plus-original-toggle.md:24-30). 모델 호출 요청·응답·usage·hash를 남기고 재생 때도 코드가 지금 검산·대사·계산한다(docs/adr/0016-record-and-replay-model-calls.md:24-35). 감사 조회는 ‘이 승인에서 읽은 카드 revision → 계산 → 입력 필드 → 원문/커넥터 → 사람/에이전트 행위·책임’을 따라가야 한다. 다음 결재자도 같은 판정 기록의 전체 항목을 받으며 S15 집합 대조가 빠진 항목을 잡는다(`docs/PRD.md:165`).

**추천이 틀리는 조건:** 배정 담당자가 결과를 열람·중단·재실행 요청할 권한조차 없어서 이름만 빌려주는 사람이라면 업무 책임자 배정은 실패다. 과도한 책임 집중 때문에 자동 처리 건마다 사람 확인을 요구하게 되면 S12와 충돌하므로 업무 분장부터 다시 정한다. 사용자가 책임을 ‘직접 확인한 진실성’으로만 정의한다면 자동 작업의 담당자 책임 모델 자체를 다시 논의해야 한다.

## 7. #10에 넘어온 나머지 결정

### 7.1 규정 개정권자·게시 권한

**추천 [설계 가정]: 규정 3종의 개정 승인권자는 대표이사, 게시 실행자는 경영지원본부장.** 인사·총무·재무는 해당 조항의 개정안을 작성할 수 있지만 승인·게시 권한은 자동으로 얻지 않는다. 게시물에는 대표이사의 승인 기록·규정 코드/판/시행일·원본 해시·게시자의 ID가 있어야 한다. 내부감사는 읽고 이의를 제기할 수 있을 뿐 게시·수정할 수 없다. 대표이사의 위임 전결이라는 개념(`CONTEXT.md:49`)과 3팀 위의 경영지원본부 구조(`docs/company/org.md:8-13`)를 근거로 **새 권한을 제안**하는 것이며 기존 조항으로부터 확정된 권한이라고 주장하지 않는다.

MVP는 판 1만 적재하므로 게시 기능은 운영 명령의 권한 계약까지 정하고, 실제 새 판 활성화는 옛 판 보존·동시 판 실행 계약이 갖춰지기 전 차단한다. 규정 파일의 기계 판독 블록이 유일 원본이고 별도 정책 값 테이블을 만들지 않는다(docs/adr/0005-policy-source-of-truth.md:30-32). `APV-9-3` 값 변경은 새 판 게시만으로 실행 범위가 늘지 않으며, 지원하지 않는 조합은 오류다(docs/adr/0014-apv-9-3-exposed-declaratively.md:27-33). 대표이사 승인 기록이 없으면 배포 운영자가 파일을 올렸다는 이유만으로 게시권을 얻지 않는다.

**반증 조건:** 개정마다 대표이사 확인이 데모 범위를 넘어 불필요한 운영 병목을 만들고 사용자가 본부장에게 위임하는 편을 원하면 권한안을 바꾼다. 단 admin에 게시권을 합치는 대안은 ADR-0002 개정 없이는 채택할 수 없다.

### 7.2 회계 장부의 계정 분류

**추천 [설계 가정]: 회사 내부 모의 계정 목록은 두되, LLM의 회계 계정 확정·세무 판정은 두지 않는다.** `supplyCategory`(택시·숙박 등), `travel_item`(일비·숙박비·교통비·등록비), `ledger_account`를 별도 열로 둔다. 다음은 **법정 표준 계정 코드가 아닌 합성 장부의 표시 분류**다.

| 모의 계정/구획 | 대응 | 확정 주체·경계 |
| --- | --- | --- |
| `TRAVEL_DAILY` 여비교통비/일비 | TRV 일비 | 코드가 제안, 재무의 모의 전표 확정 |
| `TRAVEL_LODGING` 여비교통비/숙박 | TRV 숙박비 | 동일 |
| `TRAVEL_TRANSPORT` 여비교통비/교통 | TRV 교통비 | 동일 |
| `EXHIBITION_REGISTRATION` 전시회 참가등록비 | TRV 등록비 | 동일; 부스 임차료와 합치지 않음 |
| `EMPLOYEE_RECEIVABLE` 임직원 반환대상 구획 | 회사 선결제 본인 부담액 | 채권 회수·급여 공제 자동 실행 없음, 순액 반환 처리는 #17 |

| `UNCLASSIFIED` 미분류 | 원자료·기안 사실로 분류 불가 | 임의 여비 계정으로 매핑하지 않고 재무 확인 전 전표 확정 차단 |

근거는 여비 네 항목(`docs/company/travel-policy.md:83-85`), 여비 외 분리 목록(`:218-225`), 본인 부담 상계(`:233-237`), 범위 제외(`docs/PRD.md:130`, `:136-137`)다. 카드 업종이나 영수증 문구만 보고 기업업무추진비의 법적 해당성을 확정하지 않는다. 기안자가 적은 업무 사실에 근거한 분리 후보와 재무가 확정한 **분리 결정**을 기록한다. 접대비 제재·손금·최종 매입세액 공제는 구현하지 않는다(`docs/design/receipt-pipeline.md:2669-2670`).

장부 원화와 정책 원화는 이름·값·출처를 분리하고, 장부 원화는 모의 ERP가 준 입력 또는 재무 입력만 보존한다. `TRV-14-3`의 정책 환산액을 장부 확정값으로 복제하지 않는다(`docs/company/travel-policy.md:326`). 분류 이름은 계산 규정을 새로 담지 않는 adapter mapping이며, 지급 자격·한도 규칙이 필요해지면 TRV/PRC 규정 후속으로 보낸다.

**반증 조건:** 시나리오의 핵심 목표가 복식부기 균형·세무 계정 판정이라 이 표시 분류만으로 인계를 보일 수 없다면 범위 결정을 다시 열어야 한다. 현재 제외 사항을 우회해 회계 엔진을 추가하지 않는다. 미분류로 재무에 추가 질문·재확정을 보냈다면 일반 지급 업무라는 이름으로 숨기지 않고 실제 추가 접촉·배정 기록에 넣으며, 구체 지표 포함 범위는 #11에 함께 넘긴다.

### 7.3 방향 분류기 실행 자산

**추천: 방향 분류는 전처리의 격리된 job 계약으로 두고 자산 검증 전에는 준비 완료라고 하지 않는다.** #9가 확인한 상태는 12-class 가중치는 존재하나 설계의 4-class 체크포인트·실행 코드 공개는 확인되지 않았다는 것이다(`docs/adr/0015-typescript-web-stage-sse-no-unverified-answer-text.md:70-72`, `docs/research/tech-stack-comparison.md:111`). 이번 레인은 가중치·라이선스를 새로 검증하지 않았다 **[미확인]**. 12-class를 임의로 네 각도에 접지 않는다.

#18 후속/구현 phase의 완료 산출물은 checkpoint·코드·라이선스 출처와 hash, 입력 규격, `0/90/180/270` 출력 의미, EXIF 적용 순서, 좌표 역변환, 실패 종류와 실행 가능 표본이다. Python 전용이면 docs/adr/0015-typescript-web-stage-sse-no-unverified-answer-text.md:29의 사이드카를 사용한다. #11이 방향 정답 집합·판독 품질을 검증한다. 자산을 못 확보하면 `ORIENTATION_ASSET_UNVERIFIED`라는 운영 차단을 내며, **EXIF만으로 내용 방향 분류까지 완료했다고 표시하지 않는다**. 공개 데모에 정방향 fixture를 쓰는 것은 #1의 시연 선택일 뿐 일반 전처리의 수용 조건을 충족하지 않는다.

**반증 조건:** 검증된 경량 대체물이 같은 입력·출력·좌표 계약과 #11 품질 조건을 충족하면 특정 연구 모델 채택을 버린다. 방향 교정의 실제 이득이 없다면 #18의 ‘넣는다’ 선택 자체를 ADR 개정 제안으로 재논의한다. 지금 임의 대체 모델을 확정하지 않는다.

## 8. ADR 후보 — 문서 안의 초안만

가번호 0018부터이며 실제 `docs/adr/` 번호 선점이 아니다. 함수명·도구명·루프 횟수처럼 쉽게 바꿀 것은 ADR로 올리지 않는다. 다음 선택은 권한과 감사 계약이므로 나중에 바꾸면 기존 기록 해석까지 바뀐다.

**ADR 개정 제안:** 기존 #9의 채택을 뒤집는 제안은 없다. 다만 docs/adr/0011-messages-api-direct-waits-are-document-state.md:35의 ‘반려·보류 이후’를 ‘#17이 아직 정의하지 않은 구체 전이’로 좁혀 읽는다는 명확화가 필요하다. 반려 권한을 항상 허용하는 계약과 미정 전이를 실행하지 않는 계약 사이에서, #17 완료 전 실행 거부를 ‘정상적인 반려’로 오인하지 않게 해야 한다. 해당 줄을 이 작업에서 수정하지 않는다.

S1~S16 측정 소관은 `docs/PRD.md:147-178`이다.

구현 검증에 넘길 실패 사례는 다음과 같다. 시험 구현이나 합격 선언이 아니라 **필요 검증 계약**이다.

1. 책임자 미배정·타 세계 ID·다른 역할로 호출해 모델/커넥터가 시작되지 않는지 확인한다.
2. 모델 응답 수신 전후·결과 커밋 직전·임대 만료 시 종료해 중복 필드 버전·감사 없는 전이·늦은 반영이 없는지 확인한다.
3. 판독 원본에 업무 명령 지시문을 넣어 A가 B의 조회나 쓰기 권한을 얻지 못하는지 확인한다.
4. 같은 숫자를 반대 방향으로 서술한 답변, 다른 판 조항, 비연속 합성 인용이 표시되지 않는지 확인한다.
5. 카드 미도착·끝4 지면 부재·후보 복수·값 모순을 구별하고 실제 사람 접촉 수와 필요 판정 수를 감사 원기록으로 재구성한다.
6. 사전승인→총무 연결→인사 근태→정산 재무 동의→전결→지급을 같은 사건으로 추적한다. 반려·재상신/미정 후속은 #17을 채운 뒤 실행하고, 그 전에는 성공 처리되지 않는지 확인한다.
7. 승인자가 읽은 카드의 판정 항목 집합과 계산 기록 집합을 비교하고 독립 평가기로 숫자·기한·결재선을 다시 계산한다. 제품 함수를 두 번 부르는 검증은 독립으로 세지 않는다(docs/adr/0013-postgres-object-storage-isolated-by-world-id.md:37).

이 제안으로 닫는 것은 에이전트·도구·책임의 경계다. #17·#20·#21·방향 자산 같은 명시적 공백을 남긴 채 제품이 모두 실행 가능하다고 결론내리지 않는다.
